# Subagents

[Home](../README.md) · English | [简体中文](agents.zh-CN.md)

`agent/config.yml` disables OMP's built-in subagents (`task`, `scout`, `sonic`, `security-reviewer`) in `task.disabledAgents`; they are rejected at preflight even if listed in `spawns`. `agent/agents/*.md` contains the selectable worker/advisor definitions and `reviewer` (a copy of OMP's bundled review agent that overrides it by name) (see [`agent/agents/README.txt`](../agent/agents/README.txt) for frontmatter pitfalls; keep non-agent notes as `.txt`).

The subagent setup follows these design principles:
1. **Cross-model complementarity**: trading a small amount of call latency across subagents combines distinct model traits — `claude-opus` for open-ended design (`discuss:divergent`, `task:high`) and DeepSeek V4.1 Flash for execution, conservative discussion and mentoring (`task:mid`, `task:low`, `task:free`, `discuss:steady`, `mentor:default`) — keeping reasoning variance bounded across models.
2. **Every binding resolves where this repository is applied**: chains name only channels whose credentials the machines carry (`anthropic`, `commandcode`) and keep no fallback link that cannot answer; agents listed in `task.disabledAgents` carry no binding.
3. **Stateless `task` runners vs runtime-bounded advisor roles**: because a parent agent's prompt passes its own framing into the child, general execution uses stateless `task` runners (`task:high/mid/low/free`, differentiated by model and trust) orchestrated by the main agent rather than fixed workflow nodes or role-play personas (built-in `scout` and `security-reviewer` are disabled). Predefined non-`task` roles are introduced only when a strict role boundary is required — keeping advisors independent of the caller's summary without taking over the main agent's decision — and are enforced through runtime constraints ([`user-prompt-inject`](#user-prompt-inject) injecting root user prompts, read-only tools on `discuss:*`, and `tools: []` on `mentor:default`), limiting advisor roles to `discuss:steady`, `discuss:divergent`, and `mentor:default`; `reviewer` is the one review role.

## Subagent Definitions and Model Bindings

Responsibilities, tool limits, and `spawns` lists live in `agent/agents/<name>.md`; model chains live in `agent/config.yml` under `task.agentModelOverrides` (when a model change alters a tier's class or cost, update its `description` in `agent/agents/<name>.md` and this table together). `config.yml` sets `task.structured: true`: every task child must deliver its result through `yield`, which is also the call `task-completion-judge` intercepts. Every definition except `reviewer` declares the same `output` schema, `{ report: string }`, so a parent receives the result as `report`; `reviewer` keeps the bundled verdict schema (`overall_correctness`, `explanation`, `confidence`, optional `findings`); a caller's `outputSchema` still overrides it for that call.

### Project-level subagent of this repository

`.omp/agents/consult-carbon.md` defines `consult:carbon`, discovered only in sessions whose working directory is this repository; its model is bound in the project `.omp/config.yml` under `task.agentModelOverrides` (`google-antigravity/gemini-4-carbon:high`), which deep-merges into the global overrides. It is a consultant and discussion partner with `tools: read` only, so it cannot search, list or run anything: the caller prepares the material — paths with line ranges, and command output, logs or diffs written to `local://` files — and asks open questions. It refuses a yes/no question that carries its own answer and rewrites it as the open question behind it.

## Advisor Context and `user-prompt-inject`

By default, a subagent only sees the prompt its caller passes in `task` and `context`. The following settings keep `mentor:default`, `discuss:steady`, and `discuss:divergent` grounded in the user's actual request and the repository's code:

1. [`user-prompt-inject`](#user-prompt-inject) prepends the human user's prompts from the root main session to every model call of `mentor:default`, `discuss:steady`, and `discuss:divergent`.
2. Consequential decisions consult both `discuss:steady` and `discuss:divergent`; follow-ups on the same topic message the existing agent via `write agent://<id>`. The main session receives this rule and the `mentor:default` rule from the [`append-system-model`](prompts-and-context.md#append-system-model) fragment `APPEND-SYSTEM-decision-support.md`, in full mode and not while the main model is `claude-opus-5-5`.
3. `mentor:default` has `tools: []`, so the calling agent must write out the concrete file paths, symbols, commands, and observed outputs it relies on rather than passing file names for the mentor to open.

### user-prompt-inject

Source: `agent/extensions/user-prompt-inject/`.

On every subagent `context` event (initial spawn, `write agent://<id>` wakes, and parked resumes), walks `ctx.agent.parentId` in `AgentRegistry` up to the root main session (including from depth-2 grandchildren spawned by `task:high`), reads non-empty text messages on the main session's active branch (`getBranch()`, pre-compaction messages included; a subagent that OMP runs in a subagent worker thread reads the same branch from the root's persisted transcript, along the path ending at its last entry) with `role: "user"`, `attribution: "user"`, and not `synthetic`, plus the user's answers in that branch's `ask` tool results, renders matching `PROMPT-INJECT-<label>.md` templates, and prepends one request-only developer message (`<user-prompt-inject name=…>`) without persisting it to the session file:

- **Template discovery**: scans `~/.omp/agent/extensions/user-prompt-inject/PROMPT-INJECT-*.md` and `<dir>/PROMPT-INJECT-*.md` / `<dir>/.omp/PROMPT-INJECT-*.md` from `cwd` up to the git root or the home directory, whichever comes first (only `cwd` when neither bounds the walk). The repository ships `PROMPT-INJECT-user-goal.md` (`target: mentor:default, discuss:steady, discuss:divergent`, `name: user-goal`, `enabled: true`, body using `{{user_prompt[0:e]}}` and `{{ask_answers}}`).
- **Placeholders**: `{{user_prompt[0]}}` (first), `{{user_prompt[-1]}}` (latest), and `{{user_prompt[a:e]}}` (half-open slice supporting negative indices, rendering each item as `<user_prompt index="N">…</user_prompt>`). `{{ask_answers}}` renders every answered `ask` call on the root branch, oldest first, as `<ask_answer index="N">…</ask_answer>` with one `question → answer` line per answered question (a cancelled or refused ask is left out; nothing renders when there is none), so advisors see decisions the user made in `ask` and can tell them apart from typed requests. Any other `{{user_prompt…}}` / `{{ask_answers…}}` syntax logs a warning and skips the file.
- **`attribution: "agent"` on extension messages**: `pi.sendUserMessage` defaults to `attribution: "user"` when omitted. Every extension in this repository that sends user-role messages (`watchdog-agent`, `turn-judge`, `tool-policy-nag`, `wt-tool`, `harness-restart`, `child-memory-warning`) passes `attribution: "agent"` so extension messages are not collected as human prompts.

## Dispatch Rules and Worktree Isolation

- **Agent selection**: choose and dispatch agents according to each agent's definition text (its `description` in `agent/agents/<name>.md`).
- **Recursion depth limit (depth 2)**: the main session is depth 0 and its children are depth 1. `task:high` is the worker tier that can fan out executable task slices. OMP strips the `task` tool at depth 2, so grandchildren must receive directly executable leaf tasks.
- **`agent` and `effort`**: ordinary `task` requires an explicit `agent` to avoid a disabled default. Omit `effort` unless the user asks.
- **Worker workflow**: each `task:*` worker must read the relevant code and review its plan with `mentor:default` before editing (except at depth 2). A work slice (it changes files, config, git or external state) tracks its steps in `todo` without yielding while open items remain or using `drop`/`rm` to shrink the assignment; a non-work slice (investigation, discussion, answering a question) has no `todo`.
- **Parallel writers and `isolated: true`**: when two or more writing agents run concurrently on the same repository, every writer must explicitly use `isolated: true`. Read-only shared agents remain reachable for follow-ups; plan mode forces shared read-only children. Use repository-relative paths inside isolated assignments. `task.isolation.merge: branch` cherry-picks child commits with their messages and Todo trailers; check the returned merge/no-change result.
