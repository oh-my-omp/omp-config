## Task Dispatch and Yield Checks

### isolation-nudge

Source: `agent/extensions/isolation-nudge/`.

Runs at `tool_call` on `task` in main and subagent sessions; `fork_task` is not checked by this extension. Forks with `agent` default to isolation, while forks without it default to shared cwd, so concurrent fork writers must explicitly set `isolated: true`. When a `task` call would leave $\ge 2$ write-capable agents (`task:*`, built-in `task`, omitted `agent`, `m1`, etc., counting both the current batch and running shared writer jobs from the same session) in the same working directory with at least one item leaving `isolated` unset, it blocks the call once per SHA-256 of the item's `task` text and asks for `isolated: true` on writers and `isolated: false` on read-only items. A second call with the same `task` text passes.

### task-split-check

Source: `agent/extensions/task-split-check/`.

Runs at `tool_call` on `task` and `fork_task`. Judges items concurrently under a shared 25 s timeout, asking every applicable yes/no check of one item in a single model request, and blocks the whole call if any item fails:

- **Models**: queries the OMP model role `@task-split-check` (assigned in `/model`, stored in machine-local `modelRoles`), then the `default` role chain, resolved per call. Uses `medium` reasoning unless the role entry has a `:level` suffix; on provider error, moves to the next model in the chain.
- **Split coverage**: the `split` check covers `task` items whose `agent` definition declares `splitCheck: true` in its frontmatter (the shipped `task:low`, `task:free` and `task:mid` definitions declare it; resolved with the same lookup the task tool's spawn preflight uses). The `report-limit` check applies to every `task:*` agent regardless.
- **Failure handling**: with no usable model or verdict (including request errors, timeouts and unparseable answers), the call fails open. Every judged call logs `task-split-check verdicts`.

Retry identity is the rendered prompt containing shared `context` and item `task`, with each trimmed. Both must stay unchanged for a retry to reuse a verdict.

| Check | Scope | Question | Cache and retry behavior |
|---|---|---|---|
| `split` | Main-session `task` items whose `agent` definition declares `splitCheck: true` | Checks the item's `task` text alone (shared `context` is background): does it combine multiple unrelated topics in one worker (by topic, not file count)? | Caches all verdicts (`pass-repeats`): because topic boundaries can be a judgment call, if the caller confirms it is one topic and resends unchanged shared `context` and item `task`, the second call passes. |
| `report-limit` | Items with `agent` set to `task:*` or omitted, in `task` and `fork_task` of any session | Checks both shared `context` and item `task`: does it cap the length of the worker's report (words, lines, paragraphs, tokens, or "brief report"; length limits on files the worker writes do not count)? | Caches only passing verdicts (`skip-clear`): capping a worker's report truncates evidence the parent needs, so the cap must be removed (long reports can be written to `local://<name>.md`) and unchanged retries stay blocked. |

### task-completion-judge

Source: `agent/extensions/task-completion-judge/`.

Runs at `tool_call` on terminal structured `yield` calls inside subagents whose definition declares `completionJudge: true` in its frontmatter (the shipped `task:free`, `task:mid` and `task:low` declare it; other subagents, main sessions, error yields, and incremental yields are skipped):

- **Input (60k-token budget)**: takes the assignment from the branch's last `session_init` (ignoring inherited `fork_task` history before it), the system prompt's shared background, the worker's Todo `goal`, the `yield` payload (up to 6,000 chars), and the newest contiguous sequence of tool calls and results after `session_init` that fit the remaining budget (up to 800 chars per call argument and result, keeping 60% head + 40% tail when truncated; estimated at 1 token per ASCII char and 2 tokens per non-ASCII char).
- **Models and criteria**: queries `@task-completion-judge`, then the `default` role chain, resolved per call, `low` effort unless `:level` is set, 25 s timeout, moving to the next model on provider error. Returns `DONE` or `NOT_DONE`. If the worker's Todo `goal` narrows the assignment, its stated measure never appears in the tool calls, or the work falls short of `doneWhen` (reporting a blocker included), the verdict is `NOT_DONE`.
- **Bounce rules**:
  1. The first `NOT_DONE` blocks `yield` with the reason so the worker finishes and verifies the work.
  2. After `DONE`, the extension queries `omp-todo-more:read` and blocks once if any `pending` or `in_progress` items remain (`blocked` items do not block), listing their explanations so the worker updates its Todo list first.
  3. Each bounce happens at most once per subagent session so a blocked worker cannot get trapped in an infinite bounce loop; after passing, subsequent `yield` calls in that session are not judged. The verdict is only logged (`task-completion-judge verdict`); the `yield` data keeps the agent's `{ report }` schema. Config, model, or plugin-read errors log a warning and fail open.

### subagent-usage

Source: `agent/extensions/subagent-usage/`. The agent-side counterpart of the human `/usage`: the read-only tool `subagent_usage` (no parameters; main and sub sessions, full and light mode) estimates how many more times each available subagent can be dispatched before the provider quota of its first bound model runs out. The repository ships no calibration data; each machine calibrates from its own sessions and usage history, and only after a human consents.

- **Consent**: the machine-wide `subagent-usage.enabled` setting of the `omp-config` plugin (`/settings → Plugins → omp-config` or `omp plugin config`; a project override cannot grant it), written only by the human command `/subagent-usage on|off|status|recalibrate|reset`. `on` is consent to read this machine's session transcripts and usage history and starts the first calibration in the background. Without consent nothing is read and the tool is inactive; consent is re-checked before each calibration, before its result is written, and in every tool call. `off` stops a running scan and keeps the data unused; `reset` deletes it; `status` reads only the stored metadata. No model is called anywhere: calibration is deterministic code.
- **Calibration**: a Bun Worker reads every transcript under the sessions root, judging each line on its first 256 bytes and decoding only the entries it needs, and keeps a per-file aggregate cache (`<agentDir>/cache/subagent-usage/transcripts.json`, keyed by size and mtime) so later runs read only new or changed files. On this machine a first full scan of 28,237 transcripts took 59 s at a 262 MB peak footprint; a cached rerun took 0.6 s. The main thread then writes `<agentDir>/subagent-usage/calibration.json` atomically:
  - **Per-dispatch averages**, computed on `on` and `recalibrate`: the mean USD of this machine's finished dispatches per agent + model + thinking level and per model + thinking level (3 or more dispatches; a dispatch qualifies when it ran wholly on the model its `session_init` resolved, recorded no fallback, and wrote `session_exit` or has been untouched for 30 minutes), plus the pooled spread $\sigma$ of ln cost.
  - **Quota constants**, over the trailing 21 days and recomputed inside a tool call once older than a day, so plan or quota changes age out: per account and limit (keyed by provider, the first 16 hex digits of an unsalted SHA-256 of the usage-history account key, limit id and window id; the file holds no raw account key, email or credential, but the fingerprint is stable and, since the key can contain an email, guessable), local spend on the models the provider strategy scopes to the limit over the limit's used-fraction increase, counting only hours where that account's limit has a same-reset snapshot pair and the provider's other accounts are idle; the smaller of that ratio and the 25th percentile of daily ratios (days that moved 5% or more, at least 3). A limit without enough history gets a recorded reason instead of a constant. A plan change on the same account is not detected: while days of both plans sit in the window the smaller ratio wins, so after an upgrade the numbers stay low for up to 21 days, and after a downgrade they drop within days.
- **Untracked channels** enter no average, estimate or price (the scan reads every transcript, since its aggregates are per file, and drops their entries): a provider without an omp usage provider, a provider whose transport models.yml customizes (`baseUrl`, credentials, `api`, headers, auth, discovery), and a model models.yml defines or whose headers it overrides. Metadata-only overrides such as context window or cost keep a model tracked.
- **First model only**: the binding resolves as in the `task` executor (`resolveAgentModelPatterns`, then `resolveModelOverride` on the first pattern alone). Later comma-separated fallbacks never enter any number; a first model missing from the model registry is reported as not tracked.
- **Per-dispatch estimate**: every eligible dispatch (same rule as the per-dispatch averages) of the agent on its first model whose transcript changed in the last 21 days, from the project's sessions, i.e. the session directory of the top-level session the caller descends from (followed through `AgentRegistry` parent links, so a subagent, isolated or not, pools the same sessions as its main session) plus its git and agent-managed worktrees (`worktreeSessionDirs`). Each tool call rescans through the per-file cache, so only transcripts changed since the last scan are read. With $n \ge 1$ the estimate is the lognormal mean $\exp(\overline{\ln c} + \sigma^2/2)$ with this machine's $\sigma$ (the arithmetic mean without a local $\sigma$ or when a dispatch cost 0); with none in the window, this machine's average for the agent on that model, else for that model; else no estimate.
- **Quota**: reports from `AgentSession.fetchUsageReports`, the source of the human `/usage`. Each live report is matched to its usage-history account by account id, email or fetch time. Per account, the provider's ranking strategy keeps the limits that apply to the model (plan gate, `scopeLimitsForReserve` or `scopeLimits`), windows whose reset has passed are dropped, and each remaining fraction is priced with that account's constant; the account contributes its smallest priced limit, and an account with any applicable limit lacking a constant contributes nothing and is named. Accounts are summed, since OMP routes each request to an account with headroom; a partly priced pool is labelled a lower bound.
- **Output**: rules first (counts in one pool are alternatives and never add up; refills at resets are not counted; only first models count; PENDING, NOT TRACKED and NO ESTIMATE mean no number, never unlimited), then one `POOL <provider>` section per provider whose agents share its quota, each agent line giving the count, the per-dispatch USD with its source and confidence, the quota left and the tightest limit with its reset time; then PENDING (quota exists but cannot be priced yet) and NOT TRACKED lines.

## `JUDGE`-Backed Extensions

`turn-judge`, the `intent` lane of `tool-policy-nag` (when `detector: jev`), the option mode of `watchdog-agent`, and `lang-nag` call `openJudge` in `agent/extensions/_shared/judge.ts` with their own name as the purpose. The purpose labels usage entries and is also the name of that extension's model role (`@turn-judge`, `@tool-policy-nag`, `@watchdog-agent`, `@lang-nag`, listed in `agent/config.yml` `modelTags`):

1. When `@<purpose>` resolves chat models (assigned in `/model`, stored in machine-local `modelRoles`), those models answer with prompted judgment (`TextJudge`) in chain order. OMP's judge-role chain is skipped, so no native or on-device judgment model answers that purpose. Bind the role when the `judge` model answers one extension's question badly, for example a native judgment model that reads English replies as Chinese for `lang-nag`.
2. Otherwise `openJudge` builds OMP's judge-role chain (`resolveJudge`: `modelRoles.judge`, then `retry.fallbackChains.judge`, or OMP's built-in judge defaults). Candidates without credentials are skipped; a provider error moves to the next candidate (401/402/403 cools that candidate down for 5 minutes); abort or timeout stops immediately. From the first native judgment API model onward, OMP keeps only native candidates, and `openJudge` never appends the session model.
3. There is no chat fallback: when the chain resolves no model, `openJudge` reports inactive, and when its candidates fail, the judgment fails — the calling extension's own failure policy applies. A chat fallback is expressed by binding `@<purpose>` itself.
4. Prompted answers are one-hot (the chosen option has probability 1), so thresholds below 1 act on the pick alone. Every request records usage in the session ledger with the purpose; prompted requests also record the role whose model answered. Identical native requests use OMP's judgment cache, prompted ones do not. Role assignments are re-read on every call.

### tool-policy-nag

Source: `agent/extensions/tool-policy-nag/`. The `form`, `intent` and `risk` lanes run in the main session only; the `pty` lane runs in main and sub sessions.

Inspects host `bash`, `bash_bg` (including writes to `xd://bash` and `xd://bash_bg`), and `eval`; plugin tool calls are ignored by every lane. The `pty` lane refuses calls at `tool_call`, before they run. The `form`, `intent` and `risk` lanes never block: they judge each call at `tool_result`, once it has run, and return their reminders as that result's `additionalContext`, so a reminder reaches the model with the call's result instead of steering the running turn (a steer would push the turn's other running `bash` calls to the background). They use host-tool routing violations as a signal that a model has drifted from the static system prompt during a long session: `form.prompt` is phrased as a direct observation, rather than a system notice. The heuristic detector intentionally does not minimize false positives: observed false triggers cost only a small number of self-reflection tokens without other adverse effects.

Reads the `tool-policy-nag.*` settings of `omp-config` on every watched call (the project's `.omp/plugin-overrides.json` wins over the machine values; without a readable value nothing runs). The manifest `agent/extensions/_shared/package.json` carries the defaults: `detector: heuristic`; `form.prompt` `你为什么不遵守system prompt，反思自己以后继续。`, `form.afterHits` `3`, `form.maxNags` `3`; `intent.threshold` `0.5`; `risk.enabled`, `risk.minCommands` `4`, `risk.minChars` `600`, `risk.minPrograms` `3`; `pty.enabled`.

- **`pty` lane (`pty.ts`, blocking, main and sub sessions, no model)**: runs first in `tool_call`, under either `detector`, when `pty.enabled` is on and the calling session's active tools (`pi.getActiveTools()`) include `exec_command`; without either it lets everything through. It refuses, before any process starts, a `bash` call (direct, through `xd://bash` — refused at the outer `write` — or through the eval `tool.bash` bridge; `pty: true` does not exempt it) or an eval cell that runs a command of these kinds:
  - **passthrough** — handed to another machine, container, user or shell: `ssh` (not `-G`/`-V`/`-O`), `mosh`, `vagrant ssh`, `gcloud compute ssh`, `aws ssm start-session`, `docker`/`podman`/`nerdctl` `exec`/`run`, `docker compose`/`docker-compose` `exec`/`run`, `kubectl` `exec`/`run`/`debug`/`attach`, `incus`/`lxc` `exec`/`shell`, `pct exec`/`enter`, `qm guest exec`/`terminal`, `orb`/`orbctl` with `-m` or `run`/`shell` or nothing, `limactl shell`, `multipass exec`/`shell`, `distrobox enter`, `nsenter`, `su`, `bash`/`zsh`/`sh`/`dash`/`ksh`/`fish -c`, `pwsh`/`powershell -c`/`-Command`;
  - **terminal** — needs a terminal or stops at a prompt: a bare `bash`/`zsh`/`sh`/`fish`/`python`/`python3`/`node`/`irb`/`ghci` with nothing on stdin; `psql`/`mysql`/`mariadb`/`redis-cli`/`sqlite3`/`mongosh` without a query, file or stdin; `vim`/`vi`/`nvim`/`nano`/`emacs` (not `--batch`/`--headless`), `htop`, `btop`, `top` (not `-b`/`-l`), `lazygit`, `lazydocker`, `tig`, `k9s`; `git rebase -i`, `git add -p`/`-i`, `git commit` without `-m`/`-F`/`-C`/`--no-edit`; `expect`, `script`, `unbuffer`; `sudo`/`doas`/`run0` that may prompt (`sudo -n`/`-S` and `doas -n` are judged by the command they run); `passwd`; `gh auth login` without `--with-token`; `pexpect` or `pty.spawn`/`pty.fork` in a Python cell;
  - **open-ended** — does not end on its own or waits on an outside condition: `tail -f`/`-F`, `journalctl -f`, `docker`/`podman logs -f`, `docker compose logs -f`, `kubectl logs -f`, `kubectl get -w`, `watch`, `gh run watch`, `ping` without `-c`, `docker compose up` without `-d`/`--wait`, `nohup`, `setsid`, a pipeline ending in a lone `&`, `sleep` in a `while`/`until`/`for` loop body.

  Any simple command of the line decides — every pipeline stage, `$(…)` body, `;`/`&&`/`||` link, and the command behind shell wrappers — with the first hit naming the category. Eval checks only literal launches under their own names: Python `subprocess.run`/`call`/`check_call`/`check_output`/`Popen`, `os.system`, `os.popen`, `!cmd`, `%%bash`; JS `Bun.$` without `${}`, `Bun.spawn`/`spawnSync`, and child_process `exec`/`execSync`/`spawn`/`spawnSync`/`execFile`/`execFileSync`. Unreadable, nonliteral or renamed launches pass; `xargs`, `find -exec`, `parallel` and shell `eval` are not inspected by this lane. The refusal contains only a short reason (program, category and rule) plus one `xd://exec_command` pointer, never plugin usage. A refused call reaches no other lane: nothing is counted, reminded, judged or marked. Plugin calls are not parsed or judged by any lane. `RULES` in `pty.ts` is the closed registry, with hit and miss fixtures in `ci/tool-policy-nag-pty.test.ts`. Light mode disables the whole extension.
- **`detector: heuristic`**: uses the `form.*` settings and ignores `intent.*` (no JUDGE calls, `INTENT-policy.md` not read). Sets `bashInterceptor.enabled = false` in the main session's runtime settings layer before inspecting calls (subagents inherit that runtime setting too), and clears the override when `detector` changes or at `session_shutdown`.
- **`detector: jev`**: uses `intent.*` and leaves `bashInterceptor.enabled` as configured in `config.yml` (while the interceptor is on, the `form`, `intent` and `risk` lanes skip `bash`; `bash_bg` and `eval` remain watched, and `pty` runs before that skip). The `form.*` settings count alongside `intent` and remind only while `intent` cannot run (missing/invalid/disabled spec or no judge model); judge failures or 90 s timeouts warn once per reason and do not trigger `form`.
- **Facts the reminder lanes judge**: a foreground `bash` call that ran to its end carries pi-shell's execution trace (`details.trace`, omp 18.17.0 and later; parsed by `trace.ts`). For such a call the `form` lane judges the commands that actually ran — their expanded argv, function and `eval` bodies included, commands skipped by `&&`/`||` or an untaken branch left out — and counts a listing, reading or search only when output of its pipeline reached the result; redirections still come from each command's own source text, because the trace does not record them. A call that went to the background before it ended (`async: true`, auto-background, a steer), `bash_bg`, an `eval` cell, and any call without a complete trace are judged from their text as described below. A timed-out call is judged by `form` from whatever trace it left.
- **`form` lane (command parser and counter)**:
  - Parses pipes, `;`/`&&`/`||`, quotes, heredocs, `$(…)`/backticks, and redirects (`>|`, `&>`), unwrapping `NAME=value` prefixes, shell keywords (`if`/`elif`/`while`/`until`/`do`/`then`/`else`/`!`/`{`), and wrapper commands (`timeout`, `env`, `nice`, `stdbuf`, `time`, `nohup`, `command`, `exec`, `builtin`, `xargs`); skips `sudo`/`doas`/`su`/`ssh` and inspects literal `bash|sh|zsh|dash -c '…'`, `eval '…'`, and `find -exec … ;` bodies in place.
  - Counts these shell categories: listing (`ls`, `tree`, `fd`, actionless `find`, `rg --files`, `ag -g`), reading (`cat`/`bat`/`nl`/`head`/`tail`/`less`/`more`/`zcat`, `sed -n`, awk line/range selectors, single-file `jq`, single read-only `sqlite3` queries and `.tables`/`.schema`, `tar -t`/`-xO`, `unzip -l`/`-p`), searching (`grep` with files or `-r`, `rg`/`ag`/`ack` unless reading piped stdin, awk `/re/`, worktree `git grep`), editing (`sed -i`, `perl -i`, `awk -i inplace`, `mv`), writing literal content (`echo`/`printf`/heredoc `cat` redirected to a file or piped to `tee`), and inline scripts (`node`/`bun`/`deno`/`python`/`ruby` with `-e`/`-c`/`-p`/`--eval` or `-` stdin); plus `eval` file calls (`Path.read_text`, `open`, `glob`, `os.listdir`, `readFileSync`, `Bun.file`, `readdir`, `Bun.Glob`).
  - Exemptions: listing/reading/searching captured in `$(…)`, piped into `wc`/`uniq -c`/`grep -c`, passed to `xargs`, or used as `grep -q` in an `if`/`while` test; `/dev/*` targets; and `tail -f`, `locate`, `find` with `-delete`/`-exec rm`, `git ls-files`, or pathless `grep` on stdin.
  - Silently records the first `form.afterHits` (`3`) hits; after that, returns `form.prompt` with the call's result, with a UI warning, up to `form.maxNags` (`3`) times per context until the next compaction, `/clear`, or `branch_summary` (raising `maxNags` re-arms immediately). Persists state in session custom entry `mouriya.omp.tool-policy-nag.state`.
- **`intent` lane (`INTENT-policy.md`)**: starts one JUDGE `choice` request per call at `tool_call`, so it runs beside the call, across the options `list`, `read`, `search`, `edit`, `write`, `move`, `eval`, `ast`, `shell`, `mixed`, `none`. When a shell call selects anything other than `none` (or `eval` selects anything other than `eval`/`none`) with probability $\ge$ `threshold` (`0.5`), the reminder names the intent title, the built-in tool to use, and the call text. The call's result waits up to 20 s for the verdict and carries the reminder; a later verdict rides on the next watched result, or starts a turn when the session is idle. Which shell entry a command needs is the `pty` lane's question, not an option here.
- **`risk` lane (shell only, no model)**: runs when `risk.enabled` is on.
  - On a traced foreground `bash` call it reminds when at least two steps ran and one of them failed silently: a non-zero exit status that nothing tested (not an `if`/`elif`/`while`/`until` test, not negated by `!`, not a non-final `&&`/`||` operand, not inside `$(…)`, not read as `$?` by the next command), that is not a pipeline stage's SIGPIPE (141) before a later stage, and that wrote no output of its own. Function calls, `eval`, `source` and `.` stand for their bodies, whose steps are judged instead. Length, program count and writes do not matter: an all-green chain of any length is not a risk, `command -v x || echo missing`, `command -v x; echo "$?"` and `yes | head -1` are not, `git status; command -v x; echo done` is. The reminder names each silent step's expanded argv and exit status.
  - A call cut short (timeout, cancel) is not judged.
  - Every other shell call (background, `bash_bg`, untraced) keeps the text thresholds: $\ge$ `minCommands` (`4`) segments or $\ge$ `minChars` (`600`) chars, $\ge$ `minPrograms` (`3`) distinct external programs (excluding shell builtins such as `cd`, `echo`, `printf`, `export`, `source`, `test`, `mkdir`), and a write operation (redirect/`tee`/in-place edit, write binaries such as `rm`/`cp`/`mv`/`chmod`/`dd`/`tar -c|-x`/`rsync`/`scp`/`make`/`install`/`patch`, or write subcommands of `git`, `gh`, `docker`, `kubectl`, `orb`, `npm`/`pnpm`/`yarn`/`bun`, `tofu`/`terraform`, `curl`, `wget`). Sends one reminder listing the counts, programs, and write steps.

### watchdog-agent

Source: `agent/extensions/watchdog-agent/`.

Runs periodic reviews configured by `WATCHDOG-<label>.md` files in `~/.omp/agent/extensions/watchdog-agent/` and `<dir>/WATCHDOG-*.md` or `<dir>/.omp/WATCHDOG-*.md` from the live session `cwd` up to its git root (machine-local, not synced). Linked worktrees use their own root; after `/move`, discovery and matching use the destination on the next prompt or `/watchdog` command. A discovered file runs only when its `target` and optional `cwd` both match the session; `watchModel` / `watchProvider` then decide which assistant messages count toward `every`.

`target`, `cwd` and the producer regexes use the session filter in `agent/extensions/_shared/session-filter.ts`, shared with `turn-judge`: values inside one key are alternatives, keys combine with AND.

| Frontmatter field | Values and default | Behavior |
|---|---|---|
| `target` (required) | `main`, subagent name (e.g. `task:low`) or registry id, `*`, `subagents`, or comma list | Selects which sessions run this watchdog |
| `cwd` | Optional comma list of Bun glob patterns, each absolute or `~/`-prefixed; omitted = unrestricted | Matched against the live session cwd normalized with `node:path.resolve`: `/a/repo` matches that directory only, `/a/repo/**` only its subdirectories, `/a/repo{,/**}` both, `/**/worktrees/*` any direct child of a `worktrees` directory. ANDed with `target`, even `target: *`. An empty list or a relative pattern invalidates the file |
| `watchModel`, `watchProvider` | Optional; one JavaScript regex each (alternatives with `\|`), unanchored | Tested against the `model` and `provider` of each assistant message of the watched session; only actions of matching messages count, live and when restored after a reload. Empty or invalid regexes invalidate the file. `model` stays the chat reviewer's own model |
| `inject` | `system` (default) or `user` | `system`: the note, tagged `<watchdog name=… severity=…>`, is a `watchdog` custom message with `details.filePaths`, OMP's own harness-notice channel. Its wire role depends on the provider: `developer` on OpenAI Responses (e.g. `openai-codex`), a mid-conversation `system` message on Anthropic models that support one, otherwise a `user` message carrying the tag (observed on `anthropic/claude-haiku-5-5` and on `opencode-go`, whose `openai-completions` endpoint has no developer role). `user`: the note is an `attribution: "agent"` user message without a tag; a chat reviewer writes it in the same call as the human user talking to the agent (first person, colloquial, emotional to fit the severity), while JUDGE sends the option's `.prompt` unchanged. OMP wraps a user-form `steer` in its "User interjection" notice |
| `name`, `enabled` | `name` defaults to file label; `enabled` defaults to `true` | Used by `/watchdog`; duplicate names across discovered files report an error |
| `delivery` | `aside` (default), `steer`, `nextTurn`, `followUp` | How reminders are injected; system-form `aside`/`steer`/`followUp` start a turn when the session is idle. `nextTurn` waits for the next user input or subagent `before_agent_start` and joins that turn's first model call: system notes as the hook's custom message, user notes as a steer queued during prompt preparation |
| `every`, `scope` | `every` default `30`; `scope` `full` (default) or `window` | Each tool call and each non-empty text reply of a counted assistant message is 1 action; runs at `every` actions and catches up on remaining actions at terminal `agent_end`. `window` reads only messages after the last cursor |
| `maxPerContext` | Positive integer, unlimited by default | Max reminders between two compactions (compaction resets the cap count without resetting action count or `window` cursor) |
| `model`, `tools` | Chat reviewer mode (default) | Runs in an extension-less `taskDepth: 1` in-memory session; `model` tries `@advisor`, `advisor`, `@slow`, then the session model; `tools` defaults to `[read, grep, glob]` (may include `ast_grep, web_search, edit, write, bash, eval`). A first line starting with `PASS`/`OK`/`LGTM`/`NONE` passes; any other response is injected in the `inject` form |
| `instructions`, `option.<label>[.prompt\|.delivery]` | JUDGE mode (enabled when $\ge 2$ `option.*` keys are set) | Cannot be combined with `model`/`tools`/`note`; calls `openJudge` to pick a declared lowercase option and injects its `.prompt` (no `.prompt` = pass). Errors or 90 s timeouts do not fall back to chat mode |

To watch only a leader checkout, use a rule such as `WATCHDOG-LeaderScope.md`:

```markdown
---
target: main
cwd: /absolute/path/to/leader-checkout
---
Review the latest work against the leader's assigned coordination responsibilities.
```

A copy discovered in a linked worktree remains listed as `not for this session`, rather than watching that worktree's main session, and a session in a subdirectory of the configured cwd does not match either. Add `/absolute/path/to/leader-checkout/**` to cover subdirectories, or a pattern such as `/**/worktrees/*` to cover worktrees.

- **Cursor state**: stores the last reviewed position in session custom entry `mouriya.omp.watchdog-agent.cursor` and rebuilds it on resume or branch switch.
- **Own notes**: before a user-form note is sent, a `mouriya.omp.watchdog-agent.user-note` entry records its text and source files. The record is an index, not the delivery: the cap count restored after a reload or branch move counts the file's `watchdog` custom messages and the `attribution: "agent"` user messages whose text a record names, since the last compaction. Reviews skip both, so a watchdog never reviews its own notes.
- **Commands**: `/watchdog [list]`, `/watchdog on|off <name> [session|global]`, `/watchdog rm <name>`. `/watchdog add <request>` and `/watchdog edit <name> [change]` send an `attribution: "agent"` prompt to the active model that steps through **1. Draft (expected behavior, settings table, full file text, and absolute path; no file write) → 2. Revise → 3. Write after user confirmation**. Any filesystem `write` or `edit` on a `WATCHDOG-*.md` file appends its recognition status to the tool result; resource URI writes such as `out://` do not.
- **Scope visibility**: `/watchdog list` and watchdog file-write/edit tool results show the target, cwd patterns (`any` when omitted), producer regexes and inject form, and whether the file applies to this session. `/watchdog add` and `/watchdog edit` include every filter key and `inject` in the settings reference; file status reports target or cwd exclusion, rather than attributing every exclusion to `target`.

### turn-judge

Source: `agent/extensions/turn-judge/`.

Evaluates discovered `TURN-JUDGE-<label>.md` files after every turn that the model ended with `stopReason: "stop"` and non-empty text (including subagent final reports and IRC replies when `task.structured` is off). The repository ships `TURN-JUDGE-gpt-talk-only.md`; machine-created files stay machine-local.

- **Matching**: `target` (default `main`), `cwd` (comma list of absolute or `~/`-prefixed globs against the session cwd) and the unanchored JavaScript regexes `model` and `provider` (matched against the assistant message's model/provider) use the session filter shared with `watchdog-agent`; values inside a key are alternatives, keys AND. Optional comma-separated `skipTools`: if the turn called any listed tool since the previous `stop` ending, the file is skipped.
- **Frontmatter and JUDGE input**: `name`, `enabled` (default `true`), `target`, `cwd`, `model`, `provider`, `skipTools`, `inject` (`system` default, or `user`), `maxChars` (default `30000`), at least one Noul question `question.<id>` with optional `question.<id>.true` / `.false` criteria, at least one rule `when.<name>` (a conjunction such as `a >= 0.6 & b < 0.5`, each value in $(0, 1]$), and a required `prompt`; ids and rule names are `[a-z0-9_]+`, every question must appear in some rule, and the body stays empty. All of a file's questions go to `openJudge` in one request over the state `{ 时间线: [{ 类型, 内容 }], 本轮回复 }`. `时间线` starts at the last human prompt on the branch and lists `用户说`, `用户在ask中回答` (what the user chose or typed in an `ask` call, one `question → answer` line per answered question, read from the tool result by `_shared/ask-answers.ts`; a cancelled, refused or unanswered ask adds nothing), `提醒` (agent-attributed user prompts and `watchdog` / `turn-judge` custom messages, first 400 chars each), `模型想` (reasoning text, excluding redacted blocks), `模型说`, and `模型调用工具` (`name：intent`, without arguments or results), dropping the oldest entries after `用户说` when total length exceeds `maxChars`.
- **`TURN-JUDGE-gpt-talk-only.md`**: `target: main`, `model: (^|/)[Gg][Pp][Tt]`, `skipTools: wt, harness_restart`, `inject: user`. Its Noul questions ask whether `本轮回复` says some work is still not done, run, committed, pushed or verified (`says_remaining`), announces what the assistant will do next (`announces_future`), admits a mistake (`admits_mistake`), asks the user a question or for a decision (`asks_user`), or names an obstacle outside the assistant's control (`external_blocker`), and whether the user in `时间线` told the assistant not to edit, not to run anything, to stop or to only answer (`user_forbids_work`). The prompt, a user message telling the model to keep working with tools until it has a verifiable result, is sent when `says_remaining >= 0.6` together with `admits_mistake >= 0.5` or `announces_future >= 0.3`, while `asks_user`, `user_forbids_work` and `external_blocker` all stay below `0.5`. On the hand-labelled GPT main-session turns of 2026-10-10 to 2026-10-25 under `futureppo-jev/decision-model-preview`, this caught 11 of 19 premature stops with 0 of 23 labelled negatives, and triggered on 22 of 283 unlabelled turns; the previous single-choice file caught 3 of 19 on the same states.
- **Main session vs subagent delivery**: a triggered `prompt` is sent verbatim in the file's `inject` form: `system` as a `turn-judge` custom message (the harness-notice channel, with the provider-dependent wire role described for `watchdog-agent`'s `inject`), `user` as an `attribution: "agent"` user message. A file triggers when its first holding rule, in file order, is found. In the main session, judgments run in the background; a triggered file sends its `prompt` (idle starts a turn, busy queues a follow-up; nothing is sent when the user already typed or switched branches), while untriggered files merge into one `turn-judge <name>: no rule (<id> <probability> · …)` UI notification. In a subagent, `message_end` awaits judgments for up to 20 s and, once idle, sends the triggered prompts joined per inject form: user-form prompts as one message that starts the new turn, with system-form prompts joining it as one custom message, or system-form prompts alone as one custom message that starts the turn and is confirmed by its `details.deliveryId`. The new turn's reply replaces the subagent report returned to the parent (verdicts and warnings go to the OMP log).

### lang-nag

Source: `agent/extensions/lang-nag/`. Main session only.

At `agent_end`, takes the first 200 characters of the last paragraph of the last non-empty reply and asks `openJudge` whether it is written in the `lang-nag.language` setting (`omp-config`; manifest defaults `language: 中文`, `instruction: 说中文`, read at session start or switch; a project override wins over the machine value). ## Deletion

### delete-guard

Source: `agent/extensions/delete-guard/`. Main and sub sessions, full and light mode; no config, no switch, independent of `tools.approvalMode` and `bashInterceptor`.

**Guard.** A `tool_call` hook judges every `bash` call: the loop's own calls, writes to `xd://bash`, and the nested `bash` event omp emits for such a write (each event is judged; either one blocking stops the call). The bash tool runs in omp's embedded pi-shell engine (Bash 5.3 semantics) on every platform, so the text is classified in the posix dialect plus the Bash syntax that engine runs. A blocked call does not run and returns `delete-guard: …` naming the rule (deletion command or non-literal command) and the command text; it points to `delete` when the session's active tools include it, otherwise it says the session cannot delete. A guard error is logged as a warning and blocks the call.

- **What is classified**: every command the text would run, including `$(…)`, backticks, `<(…)`/`>(…)`, Bash 5.3 `${ …; }` and `${| …; }` (inside double quotes too), substitutions in unquoted here-document bodies, literal `sh|bash|zsh|dash|ksh -c '…'` and `omp sh|bash|zsh -c '…'` scripts, a quoted here-document read by a shell, and literal `eval`, `trap` and `alias` bodies, up to 8 nested levels. Text that cannot be parsed (an unterminated quote, substitution or group) is blocked.
- **Deletion commands**, whatever their arguments: `rm`, `unlink`, `rmdir`, `shred` (lowercased, basename of a path, quotes and backslashes removed: `RM`, `/bin/rm`, `\rm`), also behind `sudo`, `doas`, `command`, `builtin`, `exec`, `env`, `nice`, `nohup`, `time`, `timeout`, `stdbuf`, `busybox` and `xargs` (their options are skipped by table; an unknown option is read both with and without a value and blocks if either reading reaches a deletion), `find -delete` and `find -exec|-execdir|-ok|-okdir`, and `hash -p` mapping a name to one of them (`hash -p /bin/rm k`, which would make a later `k x` delete).
- **Non-literal commands**: a command name from an expansion, substitution, glob or brace pattern (`$CMD x`, `$(printf rm) x`); a non-literal nested shell, `eval`, `trap` or `alias` script (`sh -c "$s"`); a shell argument from an expansion (`bash "$FLAGS"`, which may be `-c` or `-s`), and an `omp` argument from an expansion before its subcommand (`omp "$SUB" -c …`); a `hash -p` path from an expansion; `env -S`; a shell reading its script from stdin other than a quoted here-document (`… | sh`, `… | omp bash`, a here-string, an unquoted here-document, no script at all); `source`/`.` of a process substitution or of standard input (`source <(…)`, `source /dev/stdin`). An unknown long shell option is read both with and without a value. Substitutions are found in here-document bodies on any descriptor, and inside double quotes `'` does not quote (`"${x:-'$(…)'}"` runs the substitution).
- **Nested Windows shells** (any platform; on Windows they are how cmd and PowerShell are reached from the bash tool): `powershell|pwsh` (`.exe`, any path) with `-Command`/`-c` or a positional script is classified as PowerShell — `Remove-Item` and its aliases `rm`, `ri`, `del`, `erase`, `rd`, `rmdir`, `[System.IO.File]::Delete`, `[IO.Directory]::Delete` and any `.Delete(` call are deletions; `& $cmd`, `Invoke-Expression`/`iex`, `-EncodedCommand` and a script read from stdin are non-literal; `-File` runs a script file and passes. The command after `=` (`$x=Remove-Item x`), `return`/`throw`/`exit`, `&` or `.` is classified like any other, and a control block's `}` ends its statement. `cmd` (`.exe`) with `/c` or `/k` is classified as cmd — `del`, `erase`, `rd`, `rmdir`, also inside `for … do`, `if …` and `(…)` blocks and after `start` (its `/d`, `/node`, `/affinity` and `/machine` values skipped), are deletions; a command name with `%VAR%`/`!VAR!` is non-literal; `cmd` without `/c`/`/k` reads stdin and is non-literal. Case never matters, and scripts nest across dialects.
- **Passes**: words that are only arguments (`echo rm -rf /`, `git rm`, `npm rm`), expansions in arguments (`ls $HOME`), literal nested scripts that delete nothing, literal script files (`bash x.sh`, `sh < x.sh`, `source x.sh`, `omp bash x.sh`), other `omp` subcommands, `-n` syntax checks (undone by `+n`), and `--version`/`--help`.
- **Not covered**: `exec_command`, programs with their own deletion semantics (`git clean`, `rsync --delete`), external programs that delete on their own (interpreters such as `python3 -c`, `perl -e`), the contents of script files, and aliases or functions the bash tool sources from the user's shell rc.

**Eval.** The same hook judges `eval` cells by their text before they run, with the same rules and reasons. A command that is not a literal string (an f-string or template with placeholders, a variable, a concatenation) is blocked as non-literal.

- **Python** (own tokenizer; a cell that cannot be tokenized is blocked): deletion APIs — the names `rmtree`, `removedirs`, `unlink`, `rmdir` wherever code names them (calls, references such as `map(os.unlink, …)`, imports; not strings or comments), and `os.remove` on `os` or an `os` alias, or imported from `os` under any name (`from os import remove as erase`). Shell handoffs — `os.system`, `os.popen`, `subprocess.getoutput|getstatusoutput`, `asyncio.create_subprocess_shell`, any call whose `shell=` is not literally `False` or `None` (`shell=flag` may start a shell), and the kernel's `!cmd`, `x = !cmd` and `%%bash` body — classify the literal command as a script of the system shell: posix on macOS and Linux, cmd (`ComSpec`) on Windows; `%%bash` stays posix. Launches without a shell — `subprocess.run|call|check_call|check_output|Popen` and `asyncio.create_subprocess_exec` — classify a literal argv (a non-literal argv[0] is blocked). The bridge `tool.bash({"command": …})` is classified too. `%time`/`%timeit` arguments, `%%capture`/`%%timeit` bodies, f-string placeholders and the expressions nested in their format specs (`f"{x:{w}}"`) are judged as Python.
- **JavaScript** (omp's own Babel parser with the kernel's options): deletion APIs — `rmSync`, `unlinkSync`, `rmdirSync`, `unlink`, `rmdir` wherever named, `rm` on an fs or fs.promises binding or `require` (`fs.promises` reached through a bound `fs`, `import {promises}` and `const {promises} = require("fs")` included), and `.delete()` on `Bun.file(…)` or a name bound to it. `child_process` `exec`/`execSync` strings are system-shell scripts (cmd on Windows); `spawn`/`spawnSync`/`execFile`/`execFileSync` are argv, or a script when the options may start a shell (`shell` not literally `false`, `null` or `undefined`, or options the code does not spell out); `Bun.spawn`/`Bun.spawnSync` argv, `Bun.$` templates (posix on every platform; any `${}` is non-literal), `tool.bash({command})` and `tool.write` to `xd://bash` are classified. Name tables have no prototype, so `toString` or `hasOwnProperty` are ordinary names.
- **Passes**: argv launches of other programs (`subprocess.run(["ls"])`), `!ls`, `%run`, strings and comments that only mention an API, `list.remove`, `Map.delete`, and any cell without these calls.
- **Not covered**: a generic name (`remove`, `run`, `exec`, `spawn`, `rm`) aliased in an earlier cell (distinctive names are caught whatever the cell), `getattr`-style dynamic access, `os.exec*`/`os.spawn*`/`pty.spawn`, and script files (`%run`, `%load`). A function definition whose body names a deletion API is blocked even when the cell does not call it.

**`delete` tool.** Registered (approval `write`, top-level) on macOS, Linux and Windows; other platforms register no tool, and the guard there says the session cannot delete. Parameters: `paths` (non-empty string array) and `mode` (`"trash"`, the default, or `"permanent"`). The tool description, the `mode` parameter and the guard's reason tell the agent to leave `mode` unset and to set `"permanent"` only when the user explicitly asks for unrecoverable deletion; "delete", "remove", "clean up" or a request phrased as `rm -rf` is not such a request.

- **Literal paths**: no `~`, environment variable or glob expansion; relative paths resolve against the session cwd. `"$HOME"` and `"*.log"` are file names.
- **Validation before any change**: every path is checked first; one refusal refuses the whole call and touches nothing. Refused: empty or blank paths, paths starting with `~`, paths that do not exist, the filesystem root, the home directory and its ancestors, the session cwd and its ancestors. Protected directories are compared by file identity (`dev:ino`), so case variants, firmlinks, bind mounts and symbolic links reaching them are refused; the check covers the path, what its text reaches through links, and a link's target. A protected directory that no longer exists (a removed cwd) is compared by spelling. A path whose `..`, `.` or trailing `/` passes through a symbolic link (`link/../x`, `link/`) reaches a different file than its normalized form and is refused. A link that passes, dangling links included, is deleted as the link itself. On Windows a bare drive (`C:`) is refused; roots are the drive root (`C:\`, `C:/`, and `\` or `/`, which resolve to it), a UNC share root (`\\server\share`) and `\\?\C:\`; spellings are compared case-folded with `\` separators; the home directory is `USERPROFILE`.
- **`trash`**: moves each path to the platform trash, restorable from the file manager. macOS runs `/usr/bin/trash -v <path>` with the path as argv (no shell); if the binary is missing the call fails before touching anything and says `permanent` is only for an explicit request for unrecoverable deletion. Linux implements the [freedesktop.org Trash spec](https://specifications.freedesktop.org/trash-spec/latest/) without `gio` or `trash-cli`: the home trash (`$XDG_DATA_HOME/Trash`, default `~/.local/share/Trash`) for paths on its device, otherwise, on the mount that really holds the path (its parent directory's links resolved), `$topdir/.Trash/$uid` (sticky shared directory) and, when any step there fails (creating its directories, writing the info file or moving the entry), `$topdir/.Trash-$uid`; it writes `files/<name>` and `info/<name>.trashinfo` (`Path=` the URI-escaped original path, absolute in the home trash and relative to the mount in a top-directory trash). A name whose `files/` or `info/` entry already exists becomes `<name>.2`, `<name>.3`, …, so an entry already in the trash is never overwritten. Windows runs `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe` by absolute path with a fixed script that calls `Microsoft.VisualBasic.FileIO.FileSystem` `DeleteFile`/`DeleteDirectory` with `SendToRecycleBin`; the path travels in an environment variable, never in the script text. UNC paths and non-fixed drives (no Recycle Bin) and symbolic links or junctions fail with the same note about `permanent`; a missing `powershell.exe` fails the call before touching anything. A failed move is reported and never falls back to permanent deletion.
- **`permanent`**: deletes recursively and cannot be undone, and only after the user confirms it. Once every path has passed validation and before anything is touched, the tool shows a confirmation listing the resolved paths, on every call (no session-wide grant). A declined, cancelled or aborted dialog, or a session without UI (subagents, `--no-ui` RPC, print mode), deletes nothing and returns an error telling the agent to leave `mode` unset; such sessions can only move paths to the trash.
- **Result**: paths run in order and each gets an `ok` or `failed` line; any failure marks the call as an error, the summary says the `ok` lines took effect, and paths already handled stay handled.

## Host, TUI and Compatibility Extensions

### child-memory-warning

Source: `agent/extensions/child-memory-warning/`. macOS (Darwin) only; enabled in both full and light mode.

On the first main session's `session_start`, opens `libproc`/`sysctl` via Bun FFI and samples every 2 s (non-Darwin platforms log one `未启用` info entry; main shutdown clears the timer and closes the library):

- Reads `ri_phys_footprint` from `proc_pid_rusage` and keys processes by `PID + kernel start time`. Tracks owned descendant OS processes of the OMP process and process groups created by observed descendants; reparented orphans (`PPID === 1`) stay tracked until exit. Subagents running in-process — on the main thread, or in a worker thread when more than 8 subagents run concurrently and `task.workerThreads` is greater than 0 — share the OMP process's memory and are not tracked here.
- Reads the `child-memory-warning.thresholdGiB` setting (`omp-config`; manifest default `4`; a project `.omp/plugin-overrides.json` entry wins over the machine value) on every 2 s scan. If the value is unreadable or invalid, tracking continues while alerts pause and each new config problem warns once.
- When an owned process exceeds `thresholdGiB`, warns once per process identity (one main-UI warning and one `attribution: "agent"` message with PID, PPID, orphan status, GiB/bytes, threshold, and 240-char command). Never signals or kills processes.

### input-polish

Source: `agent/extensions/input-polish/`. Main interactive TUI only.

Intercepts the `input-polish.key` shortcut (`omp-config`; default `ctrl+enter`, or `alt+enter` on terminals without Kitty keyboard protocol / `modifyOtherKeys`) and rewrites the input draft using `@input-polish` then the `default` role chain (with `input-polish.instruction`, manifest default `在不改变原意的前提下，改写到听起来会让人更加想努力、能激动人心，但不要太夸张。`; a project override wins over the machine values) in a tool-less `taskDepth: 1` helper session. Streams the rewrite into a read-only overlay above the editor while leaving the original draft untouched:

### wt-tool

Source: `agent/extensions/wt-tool/`. Main interactive TUI only (`defaultInactive`, enabled on main `session_start`/`session_switch`).

OMP's `/wt` and `/move` reject calls while a turn is streaming, and `ExtensionAPI` does not expose `InteractiveMode`. The extension captures the live `InteractiveMode` instance during a synchronous `ctx.ui.setEditorComponent(undefined)` call, queues the tool request, and asks the model to end its turn; once the turn hands control back (`agent_end` without `willContinue`, or with `awaitingAsyncWork` while only background jobs can resume the session) and the session is idle, it runs `executeBuiltinSlashCommand` on the TUI instance and sends the result back as an `attribution: "agent"` message (pressing `Esc` cancels the queued action). A continuation the session schedules itself (stop reminder, retry, compaction) keeps the request queued until a later end:

- **`wt`**: runs `/wt [<branch>]`. If the session is already in a linked worktree, the first call creates nothing and returns the current worktree path, branch, HEAD, uncommitted count, main checkout path, and a `confirm` hash; pass that `confirm` value on a second call to create another worktree. Its description tells the model to propose a worktree when the working tree holds changes it did not make, asking the human first when unsure whether they are interference.
- **`wt_remove`**: requires two calls. Calling without `confirm` runs a read-only check returning the worktree/main paths, `SAFE`/`UNSAFE`/`BLOCKED` status, files that removal would delete (staged, unstaged, untracked, ignored, up to 50 per category with totals), unmerged branch commits (kept on the branch), active job/subagent blockers, and a `confirm` hash bound to the worktree state. Calling with `confirm` re-checks the state when idle, runs `/move <main checkout>`, verifies the new `cwd`, re-checks the state, and calls `worktreeRemove(path, true)`, stopping immediately if anything changed.

### harness-restart

Source: `agent/extensions/harness-restart/`. Main interactive TUI only (enabled in light mode).

Queues a restart using the same idle-turn `InteractiveMode` mechanism and arming rule as `wt-tool`. Right before calling `InteractiveMode.restart()`, appends custom session entry `mouriya.omp.harness-restart.request` (`reason` and timestamp); when the restarted process resumes the session, `session_start` sends `"Harness restart completed (<time>). Reason was: <reason>. Continue what you were doing."` with `attribution: "agent"`.

### argon-long-output

Source: `agent/extensions/argon-long-output/`. Main and sub sessions, full and light mode; no config.

Cloud Code Assist sends a `functionCall` as one finished part, so while `gemini-4-argon` generates a long `write` the stream is silent after the thinking summary. OMP's watchdogs read the silence as a stall: after 300 s the wrapper aborts with `Provider stream stalled while waiting for the next event` (before the first event, `Cloud Code Assist stream timed out while waiting for the first event`), and every retry regenerates the same call and stops at the same limit. The extension acts only on models whose `api` is `google-gemini-cli` and whose id matches `^gemini-4-argon`, whatever the provider:

- **Timeouts**: the watchdogs (wrapper idle, provider first-event, provider pre-response) resolve their budget as caller option > settings `providers.streamIdleTimeoutSeconds` / `providers.streamFirstEventTimeoutSeconds` > env `PI_STREAM_IDLE_TIMEOUT_MS` / `PI_STREAM_FIRST_EVENT_TIMEOUT_MS` > `model.compat.stream{Idle,FirstEvent}TimeoutMs` > 300000, and 0 disables a watchdog. The extension fills only the compat layer of matching model rows: a value the host resolved stays; else the `models.yml` `compat` value (OMP's Google compat resolution keeps it only in `compatConfig`, so the extension carries it over); else `0`. Explicit options, settings and env therefore still win, and every other model keeps the 300 s default. Esc and session dispose still end a silent request at once.
- **Where**: each sweep patches the session model and every available registry row (rows are shared process-wide, so subagents and compaction candidates get the default too). Sweeps run on `session_start`, `before_agent_start`, `context` (before every model call) and `session.compacting`, which OMP emits on every LLM compaction path (manual `/compact`, automatic, speculative) before the summary request. Compaction picks its model from the session model and the registry rows, so a row rebuilt by a `models.yml` reload since the last turn is patched before it streams. The handler returns nothing and leaves the compaction unchanged. A context-window refit would build a row no sweep sees, but OMP gives the argon rows no window tiers, so it never refits them.
- **Prompt**: an argon session (main and each subagent, matched on its own model) receives `ARGON_PROMPT.md` (beside the extension, shipped by the repo, re-read at every delivery point) as the `omp-config/argon-long-output` delta message of [`_shared/context-delta.ts`](prompts-and-context.md#prompt-files), delivered when a prompt starts or after a tool batch and only while the context does not already hold the same text; the system prompt stays as OMP built it: no single `write` content, `edit` body or final reply over 8,000 characters; a longer deliverable is first written as a skeleton of headings and then filled one section per `edit`; an existing large file is changed by editing only the changed sections. When the session's model stops matching, a delta says the earlier one no longer applies. A missing or unreadable file warns once per reason and delivers nothing; a delta already in the context stays in effect.
- **Oversized calls**: a single call that still exceeds the backend output limit follows OMP's existing handling (`MAX_TOKENS` → `length`; a truncated function call → `MALFORMED_FUNCTION_CALL` → `error`, not executed).

### ast-top-level

Source: `agent/extensions/ast-top-level/`. Main and sub sessions, full and light mode; no config.

With `tools.xdev` on, OMP mounts every enabled tool whose `loadMode` is `discoverable` under `xd://`: its schema leaves the request's tool list and the model drives it by writing JSON to `xd://<tool>`. The built-in `ast_grep` and `ast_edit` are discoverable, and no OMP setting keeps a single tool top-level; the only exemption is OMP's process-wide `XDEV_KEEP_TOP_LEVEL` table (`todo`, `yield`, `ask`, `grep`, `web_search`), which every partition consults through `isMountableUnderXdev`:

- **Load**: adds `ast_grep` and `ast_edit` to that table (`@oh-my-pi/pi-coding-agent/tools/xdev`) and checks that OMP now keeps them top-level. Every later partition (session build, `setActiveTools`, settings reconcile, MCP refresh, plan mode, late tool registration, subagent sessions) then sends both as function tools. OMP keeps the tool instances and their settings gates (`astGrep.enabled`, `astEdit.enabled`); `ast_edit` still only previews, and the preview is applied through `xd://resolve` or discarded through `xd://reject`.
- **Late binding**: OMP may bind this extension after the session has partitioned its tools (startup deferral of extensions that register nothing needed before the first frame). On `session_start`, which OMP replays to late-bound extensions, a session with either tool re-applies its own active set once in registration order, re-partitioning it against the table; new and resumed sessions then list the tools in the same order.
- **Lifetime**: the table is process-wide and never restored; disabling the extension takes effect after a restart.
- **Failure**: a renamed export fails the load. A table that rejects the names or that OMP no longer consults is logged at load and shown as a warning on each main session start; both tools then stay devices.

### tool-topics

Source: `agent/extensions/tool-topics/` (the `tool://` handler is its `registry.ts`; who serves which topics: [Tool Topics](operations.md#tool-topics)).

Progressive tool instructions. The system prompt keeps OMP's native description of every tool; for each covered tool a [delta message](prompts-and-context.md#prompt-files) supplies its surface, which stands in for that description with the common call instructions, and a `Topics` index; the detailed call instructions are topics read on demand as `tool://<tool>/<topic>` (line selectors apply; `read tool://<tool>` lists one tool's topics with their conditions; `grep`/`find` over `tool://` search them). `SYSTEM_TEMPLATE.md` requires reading the matching topic before a call that needs it; a `TOPIC` file's `inject` entries additionally deliver it after calls to read-only tools.

- **Files**: `TOPIC-<tool>-<name>.md` with a strict YAML header (`tool`, `name`, `title`, `when`, `upstream`, optional `inject`) and a Markdown body; `SURFACE-<tool>.md` (header `tool`, `upstream`) stands in for the tool's whole description. Topics are call instructions — parameters, syntax, values, preconditions, results, error recovery — never implementation detail. `when` is the one line the index shows (“before …”, “when …”). `upstream` names the OMP version and the sources the text was checked against.
- **Coverage**: surfaces for `read`, `bash`, `task` (whose `{{native:Available Agents}}` points to the native `# Available Agents` section), `ast_grep` and `ast_edit` (top-level through [ast-top-level](#ast-top-level)), whose surfaces keep only which code work goes to them instead of `grep` or `edit` and that their paths are code globs (a bare directory also feeds Markdown files, whose paragraphs match code patterns and would be rewritten); the pattern grammar lives in their `patterns` topics. Topics for read, bash (including waiting for an outside condition), edit (hashline mode), eval, grep, find, task, write, OMP's built-in ask, ast_grep, ast_edit, and the devices debug, github, checkpoint. Simple tools — `wait`, `glob`, `web_search`, `wt`, `wt_remove`, `harness_restart` — have no topics: their native description already holds the call contract. Tools registered from an extension or plugin file keep their own descriptions and topic indexes, even when replacing a built-in under the same name (such as `omp-ask-more`'s `ask`); this extension adds neither surfaces nor indexes to them. Plugin tool instructions: `xd://<tool>`.
- **Lifecycle**: files are read once when the extension loads and the topics are put on the router as `tool://`, replacing the handler of an earlier load (subagents, isolated children); changes need a restart. At every prompt (`before_agent_start`) and after every tool call (`tool_result`), main and sub, full and light, the extension reads the system prompt without changing it and finds each covered OMP-owned tool by name in OMP's rendered layout — inline `//` comment lines above `type <tool> =`, or a `## <tool>` device section before `### Schema`. Every tool found gets a `<tool>` element: its surface, marked as replacing the system prompt's description (`description="replaced"`), or none, marked as keeping it (`"kept"`), then the index, one line per topic with its full `tool://` URL. `{{native:<Heading>}}` in a surface becomes a line that points to that section of the native description rather than a copy. The elements form one delta with source `omp-config/tool-topics`, sent only when it differs from the one already in the context; a session without `read` gets none, and one that loses `read` gets a delta withdrawing the earlier one.
- **Injection**: a `TOPIC` header may list `inject` entries `{id, tool, parameter, pattern}`: after a `tool_result` whose named string argument (dotted paths allowed) matches the JavaScript-regex `pattern`, the file's own `tool://<tool>/<name>` is delivered once per actual context as trusted `additionalContext` (main and sub sessions, failed results included, after the tool batch and before the next model call). Delivery identity is `omp-config/tool-topic-injection` + entry id; ids are unique across the catalog and stay stable while a rule is the same rule, so a session's already-delivered markers still dedup. Compaction that drops a marker makes the rule eligible again; the shared `_shared/context-delivery.ts` guard checks developer messages in the active-leaf model projection. Rules run only while this extension holds `tool://`: another handler's topics must not be injected under its marker. Shipped rules cover only calls that change nothing and are cheap to repeat (read, grep) plus `ssh … cat` misuse: a topic arriving after a mutating call is too late and stays read-before-call.
- **Failure**: each malformed or unreadable file is skipped with a warning; other files still load. An active tool whose description is not found in that layout, or whose `{{native:…}}` section is not found exactly once, is left out of the delta and keeps only its native description, with a log warning and one main-session notice per tool and reason. When OMP or another handler already holds `tool://`, no tool gets an index.

### omomp-lang

Source: `agent/extensions/omomp-lang/`.

Sets the UI language (`en` or `zh`) for person-facing text across local extensions and OMP plugins (notifications, widgets, status bar, dialogs, overlays, command/shortcut descriptions, tool labels, and renderers). Model prompts, steers, tool descriptions, tool results, and logs are not translated.

- Reads the `omomp-lang.language` setting (`omp-config`; manifest default `zh`) at machine scope only — a project override is not read, since the language belongs to the process (changes apply on the next OMP start).
- At module load, sets `process.env.OMOMP_LANG` unless the launch environment already defines it (`OMOMP_LANG=en omp`).
- `_shared/i18n.ts` `tr(en, zh)` resolves `OMOMP_LANG` → `omomp-lang.language` (read once per process) → `LC_ALL` / `LC_MESSAGES` / `LANG` (`zh*` = Chinese) → English at each call site, reading the setting directly so deferred extensions that produce text before `omomp-lang` finishes loading still use the configured language.
- `omomp-lang.language` belongs to omp-config; OMP plugins read it as part of the shared language-discovery order. Exporting it as `OMOMP_LANG` also supplies environment-only consumers and child processes. Plugin-owned behavior belongs in the [plugin references](plugins-and-modes.md).
