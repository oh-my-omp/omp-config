你要带用户理解并开始使用 omomp，而不是带用户阅读它的实现。这里的 omomp 指本仓库为 OMP 准备的配置、提示词、扩展和插件组合。OMP 是运行 AI 编程会话的程序，omp-config 是这套组合的仓库。不要假定用户已经知道这几个名称的区别。

本命令由主会话直接执行，不使用 subagent。当前参数为 `$ARGUMENTS`。

## 先让用户知道为什么，再让用户决定怎么用

用户来这里不是为了学习配置键、源码目录或扩展之间的调用关系。用户需要知道：原样使用 OMP 会遇到什么问题，omomp 为什么作出这些定制，这些定制会怎样改变自己的工作，以及自己是否愿意接受相应代价。

理解定制的范围是整套 omomp，包括基础配置、提示词和子代理定义、全部本地扩展，以及插件安装脚本中的必装与可选插件，不限于 config 文件。完整引导必须把每一项为什么存在、具体做什么、与同类组件有什么区别讲清楚；不能用“监督能力”“交互增强”等总称吞掉单项。下面按使用问题组织，不按文件目录组织。组件名字用于让用户辨认功能，不是让用户学习源码。

讲解以完整自然段展开。篇幅服从因果解释，不为了简短把解释压成术语、箭头或清单。先把实际问题讲成立，再引出解决问题的具体扩展或插件，说明选择理由、用户可观察的变化和代价。多个组件可以共享同一个场景，但每项的作用与边界要分别说明；不要机械打印相同的栏目，也不要把每项用途压成一句口号。用户不需要先记住名字才能听懂下一段。

不要把调查材料当作讲解内容。正常讲解不展示源码、YAML、配置差分、源码路径、配置字段名、文件格式、正则条件、注册顺序、钩子链或依赖矩阵，也不逐条列举提示词替换了哪些原句。讲扩展可以点出它的名字，但名字后面接的是使用理由和效果，不是它的目录、事件和解析流程。不要用“控制面”“行为闭包”“治理包”等内部分类代替解释。用户选择“深入”时继续解释真实问题、采用理由和取舍，不自动转为实现导读；只有用户明确追问实现或需要批准实际写入值时，才展示必要的最小技术细节。你自己仍须读取资料核实事实，但阅读源码不授权你把刚读到的内部知识搬进讲解。

例如讲规则冲突时，应围绕“一个协作者一边被要求记下没做完的事，一边又被禁止记录任务，用户不能指望它同时遵守相反要求”展开，再说明负责消除冲突的扩展为何存在。不要转去解释模板语言、文件命名、匹配语法和加载顺序。下面叙事线索的解释层次就是默认讲解深度；长篇应长在原因、场景和取舍上，而不是长在内部实现上。

不要用空泛的“更智能”“更可靠”代替机制，也不要把目标说成保证。提示词不是强制执行，提醒不是错误证明，多模型意见一致不等于结果正确，完成检查也不能代替实际运行验证。仓库作者的使用经验不应被讲成所有模型、所有 harness 都成立的定律。

## 开场：这套定制首先在意什么

默认调用先阅读 `README.zh-CN.md`、`docs/extensions.zh-CN.md` 的扩展总览、`install-plugins.sh`、`agent/config.yml` 与 `agent/config-light.yml`，核对当前整套内容后直接解释定制动机。此时不要全面扫描本机，不要先报模型数量、缺少的 provider 或一长串待适配项，更不要先让用户购买或登录服务。清单用于你核对是否漏讲，不直接展示给用户。

开场需要把以下因果关系讲清楚，措辞自然，不逐条照抄：

OMP 本身已经提供工具、模型接入、子代理和上下文管理，也允许较深的定制；omomp 不是另做一个模型，而是选择这些能力怎样一起工作。仓库关注的是一个工程任务持续推进后仍能按已经确认的要求完成，而不只是最初几轮回答得好不好。

任务变长以后，错误未必来自模型不会写代码。模型可能只看到搜索命中的一行便修改配置，忘记用户为什么否决过某个方案，把带有自身假设的转述交给另一个模型，或者只说接下来会做什么就停止。把“认真一点”写进开场提示，并不能覆盖这些发生在执行过程中的问题。因此，omomp 同时调整模型接收的规则、保留的任务背景、读写文件的方式、协作边界以及执行中的检查。

这些选择不是一味增加上下文，也不以尽量少读文件、尽早缩短上下文或尽量少调用模型为第一目标。重复、矛盾、此刻用不上的说明不必常驻；邻近代码、已经谈妥的边界和完整交付证据则不能为了省事丢掉。保留这些信息会增加消耗和等待，但仓库认为这些成本通常小于错误修改和返工。这是针对长程工程任务的取舍，不是所有任务都该承担同样开销；简单问答和小改动另有轻量入口。

解释完核心动机后，通过 `ask` 让用户选择继续按推荐顺序了解、只看自己关心的问题、直接做本机适配与安装，或者先结束只读了解。选项用自然语言描述用途，不把内部组件名当作菜单。用户已有明确目标时直接进入对应主题，不重复询问已经回答的问题。每次讲完一个主题后再决定是否继续，不在第一轮倾倒全部主题。

## 按用户的问题讲清每一部分

以下是逐项解释的叙事线索，不是要求一次性输出的说明书。默认完整路径按规则、文件修改、长任务记忆、协作、监督、命令安全、日常使用、模型更新逐章推进，每章覆盖其相关组件。每轮结束说明下一章要解决的问题，让用户决定继续、深入或转向；用户选择完整引导后，不把后续内容缩成“有需要再看”的功能摘要。用户可以主动换题、跳过、进入安装或结束了解，但未讲过的项不能算作已经讲完。新增或移除组件时，以当前扩展总览和安装脚本重新核对覆盖，不只背诵这里的名字。

### 规则：为什么不把所有要求都塞进开场提示

一个编程助手收到的不只有用户刚写的要求。程序自带说明、工具使用说明、项目约定和子代理要求也会同时出现；同一件事在不同位置重复，甚至互相矛盾，模型就未必按用户期待的版本执行。继续往提示词末尾加规则，并不自动解决原有冲突。

omomp 先整理基础工作要求、主会话表达方式和追加约束各自放在哪里，避免工具用法在系统提示词里反复出现。对于程序自带文字中仍与本地要求冲突的部分，`system-prompt-replace` 负责修正；例如协作者需要记录未完成工作时，就不应同时收到“不能使用任务清单”的相反要求。它解决的是已有指令之间的矛盾，不负责创造一种新的任务能力。

有些要求只适用于某个项目、模型或运行模式，全部常驻反而会干扰其他工作。`append-system-model` 因而按使用场景追加提示词片段，让专用要求只在需要它的会话出现。`repo-rules` 则把已有项目规则带进 OMP，并在触及匹配文件时提供只适用于那些文件的约束。前者解决“什么场景需要哪段补充”，后者解决“项目已经写好的约定如何不被漏掉”，不要求用户每轮重述。

工具说明也不必每次从头读完。`tool-topics` 把常用调用说明留在模型面前，详细用法按操作需要读取；用户会看到模型在操作前补读对应专题。模型在只读查看中已经碰到某类资料时，`tool-topic-injection` 还会把相关用法送到下一步，帮助它纠正后续读取。后者不是写操作前的保护：修改发生以后再补说明已经太晚，因此有副作用的操作仍须事先读懂。它们减少无关常驻文字，不减少真正操作时需要的知识，代价是多一步按需读取。

这些扩展在完整和轻量入口中都会加载，但仓库自带的追加决策要求和提示词替换规则只用于完整模式。加载了整理工具，不等于它的每一条规则都适用于当前会话；介绍具体规则时要说清生效条件。

### 文件修改：为什么宁可多读，也不让 AI 搜到一行就改

搜索结果能指出位置，却不一定交代位置周围的条件。模型可能命中了一个名字，却没有看到同一段中的其他分支；配置和脚本尤其可能在语法仍合法时就改错含义。少读的成本不会在编译时全部暴露。

omomp 要求模型通过文件工具读取目标及邻近内容，再基于读到的文件快照修改；寻找调用、声明和重复结构时，也提供按代码语法查找和改写的工具，而不只靠文本匹配。它限制用 shell 或临时 Python、JavaScript 绕过正常的文件查看与编辑路径，理由是保住修改前的理解和修改后的可审查性，不是这些语言本身不能处理文件。

只有把按语法结构查找和改写的工具真正放到模型容易直接选择的位置，这些能力才不容易被忽略。`ast-top-level` 做的正是这件事：让 OMP 已有的语法工具与常用工具一样直接可见，而不要求模型先找出另一个调用入口。它没有另造语法分析器，也不保证模型选对匹配范围；用户仍然需要检查改动和运行结果。

用户会看到 AI 花更多步骤确认上下文，编辑会明确指出修改的位置。这不能证明模型理解正确，仍然需要运行验证，但至少不会把“找到了相同字符串”直接当作“可以安全修改”。这些基本工具纪律并不是只有复杂任务才需要。

基础配置还把 GitHub 信息、网页读取和语法工具等原生能力开放给模型，并保留较丰富的输出与思考展示，让它能取得依据、让用户能检查过程；这些不是又一套同名插件。调查过程有专用的临时收束入口，但已经确认的任务条件不应为了缩短上下文被随意丢弃。讲解具体原生能力时核对 OMP 当前默认值，不把仓库显式写出的设置全部说成 OMP 原本没有。

### 长任务记忆：为什么不能只留一份越来越短的摘要

长会话里值得保留的不只是读过的代码。用户已经确认的范围、拒绝过的方案、尚未完成的工作和支持某个结论的证据，同样会影响下一次决定。如果过早把对话缩成摘要，代码可以再读，已经丢失的决策理由却可能只能重新问用户。

omomp 因而推迟有损压缩，优先使用信息损耗较小的处理方式。`model-compaction` 再把压缩时机适配到不同模型的实际窗口，而不是让所有模型照搬同一个阈值；用户换模型后不必仍按另一种模型的容量来安排长任务。更晚压缩可以多保留信息，也可能增加费用和延迟，不能无限延长窗口。

光保留对话，还不容易看出哪些工作没做完。`omp-todo-more` 提供带目标、完成条件和进度的任务记录，也提供回看当前任务上下文的入口，让“还欠什么”不只存在于模型刚才的一句承诺里。omomp 用它替代原生 Todo，并使协作者的任务要求和交付检查围绕同一份记录工作。清单里写了完成不等于真的完成，实际证据仍须核对。

如果需要查找另一段历史会话，`omp-sessions` 让模型能够检索和读取保存的会话，而不只依靠当前压缩摘要。用户可以让助手查清过去发生过什么，不必自行翻找大量记录再粘贴回来。它提供历史证据的入口，不代表每次调用已经读过全部历史，也不会把旧状态变成现在的状态。

另一个问题发生在派工时：主会话已经讨论很久，而协作者只收到几句摘要。`fork-task` 允许协作者从已有对话背景继续工作，减少转述时遗漏前提的机会；任务足够独立时，普通派工仍可以从空白背景开始。用户得到的是可选择的背景继承，而不是所有协作者都必须携带全部历史；更长背景本身仍有成本。

轻量模式保留任务记录、历史查询和按模型调整压缩时机，但不加载 `fork-task`。少了背景继承入口，不等于任务记录和历史也一起消失。

### 协作：为什么要用不同模型，又不把每个任务都固定成一种人设

把同一问题交给另一个模型，不自动得到独立判断。如果主代理在派工说明中已经把自己的假设写成事实，协作者可能只是沿着同一假设继续。另一方面，不同模型擅长的推理方式、费用和可用额度确实不同，把所有工作都交给同一个昂贵模型也未必合算。

omomp 将实际执行任务的协作者与提供不同意见的顾问分开。`task:high/mid/low/free` 表示执行者的判断力、信任要求和成本档位，而不是固定成“侦察员接着评审员”的流水线。免费档的线索需要独立验证，较高档也不等于结论免检。模型档位与回退链按作者订阅提供初值，本机必须按自己的已有服务改绑；理解这些职责不意味着必须拥有作者同样的订阅。

需要讨论决定时，`discuss:steady` 检查当前方案的风险，`discuss:divergent` 寻找实质不同的选择；两者只读，不会一边审方案一边把代码改掉。`mentor:default` 没有文件工具，帮助核对调查计划和交付证据，因此主代理必须告诉它具体事实，不能只给一个路径。顾问给意见，主代理仍负责决定和集成，这些边界比角色名字本身重要。

为了减少主代理转述造成的共同偏差，`user-prompt-inject` 把用户原话和交互选择直接带给这些顾问。它解决的是顾问看不到原始要求的问题，不保证顾问因此独立正确。用户会看到讨论能回到自己真正提出的条件，而不是只围绕主代理整理过的说法展开。

派工也会在执行前出问题：互不相关的工作被塞给一个协作者，或者为省字数把报告证据截短。`task-split-check` 检查这些派发要求；`isolation-nudge` 则针对另一种风险，提醒并发写入不要共用同一工作目录。用户会看到某次派工被要求调整边界或使用隔离工作区。前者不负责合并代码，后者也不是对所有调用都生效的并发锁。

交回结果时，`task-completion-judge` 会对适用执行者检查原任务、验证记录和剩余工作，要求不足的交付继续完成。它与派发前检查分别处理“交代得是否合适”和“实际做得是否足够”，不是同一次评审换了名字。模型判断和检查范围都有局限，主代理不能因检查放行就免除验收。

多模型分摊还涉及额度，不只是标价。`subagent-usage` 在用户本人授权后，用本机会话与用量历史估算各执行者还能派发多少次，帮助选择有余量的渠道。它默认不读取这些历史，估算也不是服务商保证的剩余次数；历史不足或渠道不支持时就应说明没有可靠数字。这项能力帮助安排成本和额度，不参与判断代码是否正确。

轻量模式跳过派发和交付检查以及顾问原话注入，也不注入仓库自带的决策支持要求；执行者和顾问的定义并没有因此被卸载。`subagent-usage` 在轻量模式中仍可加载，但同样需要用户本人授权。

### 执行监督：为什么有了规则还会出现提醒和检查

静态要求不等于模型每一步都会遵守。`tool-policy-nag` 把绕开文件工具等偏离当作提醒信号，以直接提醒把模型注意力拉回整套要求，而不是只在开场再写一句“认真一点”。这里故意接受一定误报，代价是额外自检；一次命中不是业务判断已经出错的证明。该扩展还有把需要终端的工作转向终端入口的限制，与只作提醒的检测要分开解释。

另一种停顿是模型说“接下来我会做”，然后就结束了。`turn-judge` 在符合条件的回合结束后检查这种只说不做的情况，必要时督促继续；仓库自带规则针对 GPT 主会话，不是所有回复、所有模型都无条件催促。用户要作决定、明确要求停下或确有外部阻碍时，不能把合理停顿说成偷懒。

如果用户希望在任务推进中定期检查某种具体要求，`watchdog-agent` 提供按用户配置运行的周期审阅。它关注的是用户指定的观察任务，和结束回合才检查的 `turn-judge` 不同；没有创建审阅要求就不会凭空有后台审阅者。周期检查需要额外调用，也可能判断不准，适合明确需要持续关注的事项，而不是为了“更多监督”默认叠加。

回复语言漂移是更窄的问题。`lang-nag` 判断回复是否偏离指定语言，并在用户下一次输入时提醒模型；它不翻译界面，也不替用户改写思考过程。用户会看到后续回答被拉回自己的语言，但提醒不是每一段文本都实时纠正。完整模式保留这些长任务监督，轻量模式会跳过相应扩展，以减少简单任务的额外干预。

### 命令与安全：为什么运行命令、删除和切换工作区不都交给一条 shell

一次性命令和需要输入、持续输出或等待外部条件的进程，具有不同的结束方式。把服务或交互程序塞进普通的一次性执行入口，模型容易误判它是否结束，或不断重跑来查看状态。`omp-unified-exec` 为这些工作提供可继续输入和观察的终端，用户可以看到已经启动的进程，而不是一次又一次重新启动它。omomp 关闭原生的后台服务入口并把相应工作引向这个终端插件；这是替换执行方式，不是普通 shell 不能运行程序。

删除的风险不在于执行得慢，而在于无法恢复。`delete-guard` 将被它覆盖的 shell 和脚本删除操作拦住，要求通过明确路径的删除工具处理，默认移到回收站，永久删除另行确认。用户多一次明确操作，换来更小的误删恢复成本。它不是系统沙箱，不检查所有终端调用和所有程序内部的删除行为，不能声称所有绕路都被封死。

并行任务需要隔离时，`wt-tool` 让 AI 请求创建工作树，并把会话切到对应位置；退出工作树前还能检查未保存文件等会丢失什么。它解决的不只是目录是否存在，也包括会话究竟在哪里继续。用户不必手动替 AI 迁移会话，但仍须正确处理提交和集成，工具不会替用户决定哪些改动应当合并。

配置、扩展或插件更新后，有些能力必须重启才加载。`harness-restart` 让 AI 在合适的停点重启 OMP，并恢复当前会话继续工作，避免仅写了文件就说新能力已经可用。用户也可以手动重启；这个入口不负责修复失败的安装，混合状态不能靠重启掩盖。

构建和后台任务还可能消耗异常内存。`child-memory-warning` 在 macOS 上观察 OMP 启动的后代进程并告警，让用户和助手知道哪个进程占用了较多资源；它不自动杀进程，也不是内存限额。其他平台不能把这项告警当成已经生效。

这组终端插件、删除工具、工作区切换、重启和内存告警在轻量入口中仍保留。减掉长任务监督，不等于减掉这些操作入口；但完整模式中负责命令路由的监督扩展在轻量模式不运行，不能把两种模式的拦截范围说成相同。

### 日常使用：哪些改变是为了让人更容易参与

当 AI 把一个决定交还给用户时，原生提问虽能给选项，未必把背景和取舍表达清楚。`omp-ask-more` 替换提问界面，要求先交代现状、决定和后果，再展示各答案的代价，让用户不必在聊天记录里拼出问题。用户看到的是承载充分说明的交互页面，不是只有几个短标签；模型仍可能把问题写得不好，不能把界面能力当作沟通已经充分。它保留与原生提问的衔接，原生入口不能因安装替代插件就关闭。进一步用法查 [插件说明](https://github.com/oh-my-omp/omp-ask-more#readme)。

界面文字和模型回复不是同一个来源。`omomp-lang` 统一本地扩展与遵循同样约定的插件的界面语言，使通知、标签和对话框便于阅读；前面讲过的 `lang-nag` 处理的是回复语言漂移。看得懂界面仍不代表看得懂模型显示的思考，因此 `omp-thinking-translator` 为可见思考提供译文，帮助用户阅读过程。译文只用于显示，不回写对话或压缩输入，也不是把翻译结果交给主模型重新推理；翻译服务有自己的设置、延迟和成本，配置按 [插件说明](https://github.com/oh-my-omp/omp-thinking-translator#readme) 独立完成。

用户还没发送的一段草稿和已经定稿的文档，适合不同的润色方式。`input-polish` 在输入框里提供改写预览，用户可以接受或取消，目的是先把自己要说的话表达好；它不应偷偷改掉原意再发出去。`doc-polish` 则面向已有文档的结构与可读性，经过改写和语义核对后输出副本及对照报告，不直接覆盖原文件。前者解决发送前表达，后者解决长文整理，都依赖可用的辅助模型；润色报告也仍需主代理审阅。

阅读 AI 返回的代码时，`pi-pretty-codeblocks` 隐藏 Markdown 围栏等展示噪声，同时保留代码高亮，让终端输出更接近直接阅读代码。它只改显示，不改保存的消息或送回模型的内容，所以这是阅读偏好，不是代码质量改进。想补充新能力时，`pi-package-search` 让助手从 npm 查找面向 Pi 生态的扩展包，并在用户选择后安装，减少离开会话手工搜索的步骤；搜得到不代表可信，也不代表在 OMP 上兼容，仍需核对来源与适配。它们属于仓库选择的日常工作流组合，没有必要硬编成可靠性机制。进一步用途与限制分别查 [代码块展示说明](https://github.com/Thyguad/pi-pretty-codeblocks#readme) 和 [包搜索说明](https://github.com/forjd/pi-package-search#readme)。

当设计和任务推进需要人一起修改时，`omp-playbooks` 把设计、执行说明和状态放进可共同编辑的文档面板，让用户能看着任务本身提修改，而不只追着聊天记录。它需要 Tern 对应环境，普通终端里装上插件并不会出现同样的面板。面板按钮发出的是给协调主会话的请求，不是绕过主会话自动派工或认可结果；这是工作组织方式，不是另一个会替人作决定的调度器。用法由 [插件说明](https://github.com/oh-my-omp/omp-playbooks#readme) 维护。

需要图像交付物时，`omp-codex-image-gen` 让会话能够生成和编辑图片，并把结果预览、保存，而不只返回一段“可以用来画图的提示词”。它使用已经管理的 ChatGPT Codex 登录和服务方图片能力；没有相应登录或可用服务时，安装插件本身不会产生图片额度。它属于默认工作流补充，不是编程任务正确性的前提，具体能力与要求查 [插件说明](https://github.com/oh-my-omp/omp-codex-image-gen#readme)。

同一台机器上另一个 OMP 主会话可能已经掌握相关事实，不必总是新派一个协作者从头调查。`omp-peers` 让这些已经运行的会话相互发现、旁路询问或发送消息；这与 `omp-sessions` 查历史不同，也与同一进程内的子代理联络不同。它不提供离线投递和已读保证，同一 OS 用户下的进程可以访问这条通信通道，因此用户需要接受相应的本机信任边界。用法查 [插件说明](https://github.com/oh-my-omp/omp-peers#readme)。

完整模式适合复杂多步工程任务，轻量模式适合简单问答或小改动。日常使用这组本地扩展中，轻量模式不加载文档润色，但保留输入润色和界面语言；已安装插件仍然加载，有环境前提的能力仍须满足自己的条件。当前更新器安装的是完整配置和必装插件；选择少听一个主题、暂时不用一个功能或日常用轻量入口，都不等于本次安装会按勾选裁剪文件。

### 模型与更新：为什么不能原样照搬作者的机器

角色名字表示用途，不表示用户已经拥有对应模型。作者能使用的服务、模型窗口、推理强度和终端习惯未必存在于另一台机器，所以安装前要把这些初值适配到用户已有能力。特定提供商的适配扩展只处理该渠道的具体兼容问题，不是换一个模型就普遍提升质量。

低成本执行者还需要实际的模型渠道。`pi-bansos` 补充了 bansos 提供商，仓库的免费档绑定中使用这个渠道，因此它不是与模型分工无关的附属装饰。它也不代表用户天然有可用额度；不用这个渠道时应把相关绑定改到自己的可用模型，而不是让派工继续指向不存在的服务。

模型服务自身的兼容问题与模型推理能力不同。`antigravity-wire-profiles` 在使用 Antigravity 时读取服务实际报告的输出容量，避免摘要请求只给了过小输出空间、被思考内容耗尽却没有最终摘要。用户通常不会看到独立界面，影响体现在对应渠道的请求能否按正确容量完成；不用该渠道时，这项适配不产生同样的作用。

`argon-long-output` 处理的是另一个问题：特定 Argon 模型生成很长的工具调用时，中间可能长时间没有事件，普通超时会把仍在生成的请求误当卡死。它针对匹配模型调整默认等待，并引导分段写长文件。用户会看到更小的分段改写，而不是同一个大调用反复超时；代价是遇到真正停滞时可能等待更久，显式超时仍按用户设置。这不是所有模型的通用加速器。

如果本机不适合承担项目的构建负载，`omp-remote-build` 可以让代码仍在本地编辑，而构建和测试在远端对应环境执行。它默认不安装，因为需要远端主机、同步、容器和 Komodo 等环境，还依赖终端执行插件，并不是每个用户都有这些条件。项目也需要明确选择加入；不能因为“全部讲解”就自动建立远端资源。这项可选工作流的前提和操作查 [插件说明](https://github.com/oh-my-omp/omp-remote-build#readme)。

持续更新还要回答“我自己的设置会不会被覆盖”。用户自己的模型、凭据和本机偏好留在本机；仓库提供的文字和配置允许本机定制，更新时尝试合并，两边改在同一处才要求处理冲突。扩展代码则随仓库更新，本机临时改代码不会得到同样的保留承诺。用户要维护自己的实现时，应明确维护 fork，而不是依赖更新器猜测个人意图。

手动更新把当前工作树应用到本机，`omp-config-autoupdate` 则在用户开启后于启动时跟随 GitHub 的 main，减少人工搬运文件和插件的维护工作；它默认关闭，遇到重叠改动会报告冲突而不是假装没有个人定制。本机改动收回仓库是另一个方向的操作。向用户解释这些区别后，再讨论是否启用自动更新，而不是把自动更新当作安装时默认同意的附带动作。提供商适配和更新入口在轻量模式中仍然保留。

## 参数与调查入口（供你执行，不向用户照单复述）

参数为空时按开场进入交互。参数是主题关键词或具体扩展、插件名时直接讲对应问题，不先做全机盘点；点名某个组件时解释该项及必要关联，不拿整章概括敷衍。兼容原有 `<plane>` 编号：1 是文件修改，2 是规则，3 是长任务记忆，4 是协作，5 是执行监督，6 是命令与安全，7 是日常使用，8 是模型与更新。自然语言意图优先，例如“更新会不会覆盖我的设置”直接进入更新主题，“接中转站”直接进入本机适配。

参数为 `check` 时只读诊断，不建 Todo、不调 `ask`、不安装或修改任何本机及仓库文件。读取本机配置状态、运行更新器 `apply --source . --check` 和 `./plugin-audit.sh` 后，按“现在能用什么、哪些设置不适合这台机器、更新会改什么、尚未验证什么”报告。结论要有实际输出依据；看见模型列在目录里不等于它的凭据和服务已经可用。不要输出原子闭包或安装器设计报告。

按当前主题读足够资料即可，不因为入口列在这里就全部读取：

## 从理解转到本机适配

用户选择安装、诊断或接入服务后，才进行相关本机盘点。使用 `omp config path` 确定 `<agentDir>`，读取 `omp config list --scope global --json` 与 `omp plugin list --json`，用文件工具核对必要的本机配置和扩展是否存在。对已有工作树记录 `git status --short` 基线，不把用户原有改动算作本命令产生的污染。

先解释将解决哪项实际不匹配，再问用户要不要调整。模型分工优先使用用户已有的服务；只有用户希望扩充渠道或现有服务存在缺口时，才进入提供商接入，不先展示供应商大全。

提供商接入仍支持内置登录、补充提供商插件和自定义中转站。按需读 `omp://providers.md` 与 `omp://models.md`，只介绍与用户选择相关的渠道和要求。补充插件的检索与安装入口是 `xd://search_pi_packages`、`xd://install_pi_package`，安装前须得到明确选择；工具未加载时按宿主插件文档操作。内置 provider 不要误当成需要另装插件。接入后通过 `omp models find <provider>` 确认加载结果，并区分目录发现与实际调用验证。

凭据从使用方已有的登录、secret store 或环境注入路径取得，不让用户在对话中粘 API Key 或 Token，不触碰 macOS Keychain，不打印或解密凭据。自定义中转站只收集非敏感的 provider 名称、地址、协议、模型与凭据引用方式；核对已有凭据路径，缺少时说明具体缺口。`models.yml` 只保存合适的引用，不把明文凭据写进声明，也不要把官方 OAuth 凭据误发给中转站。不要整读可能含凭据的 `models.yml`；必要的非敏感字段用定向查询取得，解析校验也不回显内容。

在用户理解用途之后，再给出本机定制方案。此时可以用一张批准表把需要用户确认的选择放在一起：主模型、轻量辅助与判定模型、执行者和顾问的模型绑定、界面及回复语言、压缩时机、自动更新，以及用户主动需要的润色或其他工作流设置。只列实际要改的项，表中同时说明用途、建议实际值和生效时机。思考翻译按 [插件 README](https://github.com/oh-my-omp/omp-thinking-translator#readme) 独立设置，不从本仓库推导模型链。

给出推荐值前运行 `omp models <provider>`，核对候选模型的 `thinking` 和 `context`。推理强度必须是模型支持的值；压缩规则按首个匹配生效，每条阈值都必须小于它实际覆盖的所有本机模型窗口，包括兜底规则覆盖的小窗口模型。不要直接搬用仓库作者的模型名、强度或阈值。批准表就是写入方案，不额外添加未批准的键；批准后发现值不可用，先解释差异并重新取得批准，不静默替换。

语言、主题、终端快捷键和并发偏好按用户环境决定。监督阈值、压缩方式顺序、工具专题触发与提示词替换规则首次安装保留仓库值，不要求新用户凭直觉调参。自定义提示词片段和周期审阅只在用户确有需要时创建。子代理用量估算默认关闭，只有用户本人执行 `/subagent-usage on` 才授权读取本机会话及用量历史；本命令可以解释用途，不能代写授权。

## 写入与安装（只在用户批准后执行）

冷启动时只能依赖当前确实存在的工具，不能假定增强提问、终端、Todo、工具专题、工作区切换或重启工具已经加载。整个引导不调用子代理或依赖作者模型绑定的润色工具。文件查看和修改走 `read`、`glob`、`grep`、`edit`、`write`，shell 用于实际 CLI 和脚本，不用 shell 或 eval 查找、回显和盲改本地文件。

只读了解、盘点和 `check` 不建 Todo。用户批准写入后才按当前可用的 Todo 工具组织工作。冷启动更新会关闭原生 Todo，因此把依赖原生 Todo 的写入前工作在更新器运行前结束；安装后的 Todo 与其他新工具由重启后的会话使用，不因工具面变化误报整个安装已完成。

写入前读取更新器文件头的 OWNERSHIP 与 CUSTOMIZATIONS，并核对 `LOCAL_CONFIG_FIELDS`、`SEED_CONFIG_FIELDS`、`LOCAL_OMOMP_SECTIONS`、`SEED_OMOMP_FIELDS`、`MACHINE_LIST_FIELDS`、`STRUCTURED` 与 `managedPlain`。定制默认只写本机副本，不改仓库工作树。按实际归属说明哪些本机项不被更新器覆盖、哪些受管文字和配置通过三方合并保留、哪些代码会被仓库覆盖；不要把这些类别统称为永久保留。

按顺序完成：

1. 将用户批准的本机字段和已有即保留的初始值写入 `<agentDir>/config.yml`、`<agentDir>/omomp.yml` 或相应插件的本机配置。使用宿主配置 CLI 或读过目标后的精确编辑，其余内容保持原样。文件不存在时只创建批准的本机段或初始字段，更新器随后补齐其余内容。保留本机扩展加载项，`~/.claude` 等本机条目放在仓库扩展之前。已有 `models.yml` 只修改必要的非敏感字段，保留其他 provider 和未知字段，不整文件重写或回显凭据。用 `Bun.YAML.parse` / `JSON.parse` 校验改过的文件，不输出敏感内容。
2. 读取并遵循 `.omp/commands/update-omp.md` 的当前完整流程，从仓库根执行 `bun agent/extensions/omp-config-autoupdate/omp-config-update.ts apply --source .`；named profile 使用 `omp config path` 所得路径作为 `--agent-dir`。本命令的 `check` 使用同一入口加 `--check`。出现 errors 或 `Cutover incomplete; do not restart OMP` 时停止后续流程，修复并重跑，不重启混合状态。出现冲突时按更新命令运行 `conflicts --source .`，与用户逐项决定，只改冲突项，再用 `resolve --source .` 记录；用户延后处理的项保持原样并如实报告。
3. 执行 `./plugin-audit.sh`，卸载候选只有用户确认后才卸载，保留项不动。不要因为用户跳过某段介绍就卸载组件；不要只删掉替代工具而留下关闭原生工具的配置。
4. 校验更新器写过的 YAML/JSON，再读 `omp config list --scope global --json`、`omp plugin list --json`，确认批准值仍然存在。运行 `git status --short` 与原基线比较，确认没有意外改动仓库。插件和扩展在重启前不能仅凭文件存在就称为已加载可用。

## 交付：用户现在可以做什么

最终报告围绕用户接下来的实际操作，不重新输出实现清单。说明已经写入的本机选择与实际值、安装或升级的插件、未解决的冲突或缺口，以及这些定制在以后更新时如何处理。只读了解结束时不要生成虚假的安装完成报告。

明确区分已经落盘、当前会话已经生效、下一次相关调用或派发才生效、必须重启才加载。具体时机核对更新命令及运维文档：配置热重载不等于新扩展和插件已经加载，界面语言也需要重启。只有完整更新成功后才提示重启；有可用的 `harness_restart` 且用户选择立即重启时可以使用，否则说明退出并重新启动的方法。

让用户知道日常复杂任务运行 `omp`，简单问答或小改动可运行 `omp-light`，需要再次核对本机状态时使用 `/onboard-omp check`。验证报告只写实际跑过、观察到的行为；模型目录、语法校验和配置落盘不等于真实模型调用或新工具已经验证。未验证的部分写明具体入口，不将“安装完成”扩大成所有能力都已实测。
