## 最先确定用户语言

这是 slash command 展开的中文指令模板，不是用户的中文发言。先回看触发命令之前用户最近的真实自然语言消息及明确语言要求，确定本次语言；没有可判断的用户文字时再参考当前会话语言设置。所有面向用户的文字都使用这个语言。

如果用户语言不是中文，当前回合只做开场沟通：用用户语言建议先 fork 仓库，并把适合个人定制的配置和 prompt 改成该语言，询问是否先做。发出这条普通文字回复后就结束本回合，等待用户回答，尚不调用工具或开始调查。用户已经明确选择时按其选择执行；跳过或拒绝则保持只读，以同一语言进入下文主线。

用户接受后，先检查当前仓库是否已经是可用的个人 fork；需要新建时确认目标归属，按当前 GitHub 账号与 owner 规则操作。读实际配置与 prompt，说明本次要本地化哪些文件，再在 fork 中调整语言相关设置和文字。优先处理影响用户体验的配置值和示例提示词，已经适用的文字保留。讲解语言、UI 语言、模型提示词语言分别处理：`omomp-lang.language` 设置当前只接受 `en`、`zh`，其他语言的讲解与可定制 prompt 仍使用用户语言，UI 使用现有受支持选项；插件的语言能力到插件来源核实。

本地化保留配置键、枚举、工具和角色名、匹配条件、协议值及解析所依赖的标签。替换规则用于匹配上游原文的部分保持原文，只调整适合翻译的输出；提示词翻译保留原来的约束含义。修改后验证解析、实际加载的文字和相关匹配，再回到入门主线。本机安装另按用户授权执行，以 fork 工作树运行 `/update-omp`；当前启动自动更新拉取官方仓库，fork 维护的译文采用先同步上游、再从 fork 工作树更新的方式，保持官方启动自动更新关闭。本机专属语言值与 fork 受管文件按各自归属维护。

整个命令不用 `ask`。除上述开场选择和实际操作缺少的个人决定外，调查与讲解连续推进，不逐章确认，不询问是否继续。用户可以随时用普通对话打断或点题。

你是这次引导的调查者和讲解者。读者想知道：自己已经有了全局规则、skills 和工作习惯，为什么还需要 omomp，它能替自己承担什么，又会增加什么。先围绕这些已有资产讲清故事，再以整套组件介绍补充理解。范围包括基础配置、提示词、子代理定义、全部本地扩展和安装脚本声明的全部插件，含可选项。

现有文档、仓库配置和下文线索都是调查参考，不是现成讲稿。请亲自调查当前 OMP、omomp 和本机资料，形成自己的理解。由主会话直接完成，不派 subagent。源码用来解答问题，交付是使用与设计动机的介绍，不是开发者实现评审。

当前参数：`$ARGUMENTS`。

- 参数为空：先做本机既有规则与 skills 的替代、增强分析，再补充整套 omomp，默认只读。
- 参数是主题、扩展或插件名：围绕该项及直接相关的既有要求讲解。
- 参数为 `check`：执行后文的本机只读诊断。
- 用户明确要求适配、安装或接入服务：进入本机操作流程。

兼容原有主题编号：1 文件修改，2 提示词与规则，3 长任务记忆，4 协作，5 执行监督，6 命令与安全，7 日常使用，8 模型与更新。编号只作入口。

## 开场先讲主 agent 的能力取舍

开始介绍的第一段先讲明 omomp 的设计立场，再调用工具调查：完整定制让主 agent 承担更多工具选择、条件判断、协作编排和执行监督。对低能力主 agent，这些要求是沉重的负担；对高能力主 agent，它们能增强调查、执行和协作能力，为复杂任务的完成与交付质量提供保障。这里谈的是主 agent 的职责，不妨碍低成本模型承担边界清楚的子任务。

接着解释为什么从用户自己的规则开始：有些个人偏好、领域政策和工作规则特意留给用户，没有内置进 omomp；另一些原本只能靠自然语言反复要求模型遵守的执行约束，可以改由 omomp 的机制承担。入门先找出本机真实存在的这些关系，讲清可以少重复要求什么、仍要保留什么、额外得到什么，而不是先给用户增加一份组件清单。

## 从 omomp 之外的本机资料开始

先看当前上下文中已注入的全局规则正文、来源标识和 skill 清单，结合宿主的配置发现说明及必要的非敏感配置，定位本机已有的全局规则、skills、提示词和相关工作约定。需要定位实际 agent 目录时用 `omp config path`；发现方式参考 `omp://config-usage.md`。检查限定在实际登记或已知来源中的规则、skill 入口和相关提示词：列出规则文件与 skill 名称/描述即可定位正文，不递归枚举整个 home 或配置根目录中的会话、缓存与运行状态。

把资料来源分清：用户在 omomp 之外维护的全局资产、当前项目规则、omomp 随附示例不是一回事；磁盘上存在、当前会话已加载、采用 omomp 后才会生效也分别说明。冷启动尚未加载的规则仍可作为用户已有资产分析，加载情况按宿主与 omomp 的实际机制核实。已注入的正文直接使用；只有摘要或需核对语义时再读来源。仓库自己的示例不能冒充用户原来已有的规则。

规则按实际要求理解。skills 先了解清单、描述和用途，再读与替代分析直接相关的正文；技能通常还承载领域知识和操作流程，通用执行机制与这些知识如何配合也要讲清。只摘述支持解释所需的语义，不把本机正文或私人细节整份抄给读者。

从最容易理解的一处真实重叠开始，读取对应扩展或插件的资料、必要实现和配置。区分当前本机已经启用的行为与采用仓库示例后才会得到的行为。比较原要求与机制的约束对象、作用范围、触发时机、执行强度和失败处理，形成具体结论：哪些可以由机制承担，哪些只承担一部分，哪些继续由用户规则或 skill 提供。提醒和抽查按提醒和抽查解释，领域目标、例外与审批等没有被承担的部分继续保留。

沿这条真实要求讲故事：用户原来为什么写它，过去需要模型一直记住什么，omomp 在哪个环节接手了哪部分工作，用户现在少操心什么，仍需表达什么，以及机制额外赋予了哪些原规则本身没有的能力。再沿相邻工作场景展开其余有代表性的关系。发现重复或冲突时，把它们放回同一个故事解释，而不是只做名称配对。

这是介绍的主线。替代结论随叙事给出，来源在相应判断旁简短标明；不输出规则全文、逐条资产清单或巨大的规则—组件对照表。其余个人和领域要求归纳说明保留理由；没有找到外部资料时如实说明，再讲机制带来的新增能力。规则可能还供其他 harness 使用，OMP 内的替代不等于应从共享来源删除。默认分析不改写、迁移或删除任何本机规则和 skill。

## 用整套组件介绍补充这个故事

主线讲清后，再调查并解释尚未涉及的配置、提示词、子代理、扩展和插件。已有故事里讲透的部分只补新信息；其余部分解释用途、采用原因、用户会感受到的变化和可配置方式。这些介绍是主线之外的补充，不反过来用组件清单组织开场。

完整路径用 `README.md` 或中文版本理解设计出发点，结合 `agent/config.yml`、`agent/config-light.yml`、`agent/extensions/_shared/package.json`（`omp-config` 插件的设置 manifest）和 `install-plugins.sh` 核对组合。用 `glob` 发现 `agent/extensions/*/index.ts`、`agent/extensions-last/*/index.ts` 和 `agent/agents/*.md`，将提示词模板、主会话追加规则、`omp-light` 启动器纳入理解。插件范围取安装脚本的实际声明，包括注释的可选插件。`_shared` 是实现辅助，不是另外一组用户组件。

点名单项时，从该项自己的入口、配置和说明开始，只调查理解它所必需的关联及相关外部要求。全组合发现与全局资产盘点不是单项介绍的前置作业。账号与安装健康诊断留到 `check` 或实际适配阶段。

对扩展，阅读入口文件头、配置读取和主要行为，有具体疑问时沿调用读必要实现。对插件，阅读插件自己的 README，可以使用本地检出、已安装包或安装来源；行为与配置疑问到它自己的实现核实。对 OMP 原生能力，查阅 `omp://settings.md`、`omp://tools/`、`omp://compaction.md` 等相关内置文档；模型接入参考 `omp://providers.md` 和 `omp://models.md`。用 `docs/` 帮助定位，不把参考资料当作答案。

用途由当前实现和拥有方资料核实；采用原因从仓库设计说明、接入关系和相关记录理解。把资料明说的原因与你根据行为形成的推断分开，发现参考与现状有差异时查清后再解释。

## 把配置当作用户定制入口

omomp 通常把某种行为做成配置文件，就是为了让用户按自己的需要配置。仓库随附的内容是一组可运行的示例，不是要求所有用户遵循的唯一方案。

调查时把机制、配置接口和示例内容分开。先读 schema 和加载逻辑，理解接受哪些策略、怎样决定有效配置，再看仓库如何使用它。配置可能是 `omp-config` 插件设置（默认值见 manifest），也可能是提示词片段、替换规则、回合判定、周期审阅或子代理定义；核对作用域、覆盖或组合方式、生效时机。示例在被加载时会实际运行，一个示例取值也不代表全部合法选择。

讲清这个例子为什么这样写、哪里体现作者的模型和工作习惯、用户怎样重新组织。模型绑定、阈值、监督问题、提醒措辞、适用对象和模式沿真实接口解释。配置归属与合并规则决定更新如何处理本机修改，不限制用户定制的权利；插件自己的默认值与本仓库的示例分别说明。

## 连贯讲解与范围核对

把调查结果先在自己的推理中整理成因果关系，再沿用户的实际工作讲述。正文用连贯自然段，组件名帮助辨认分工，篇幅用在场景和理由上。可配置性讲到能改变什么策略、仓库示例选了什么、另一个需求如何组织、在哪个范围何时生效；具体语法留到用户实际配置时，调用细节留到追问实现时。正文不铺源码、配置值对照表、schema 字段列表或内部事件流程。

可沿现场形成的关系调查提示词冲突、文件操作、长任务记忆、执行者与顾问、监督时机、终端与工作区、日常交互、提供商和更新。这些是参考方向，不是固定章节或预写答案。每组讲清后直接继续。

结束前内部核对本次范围：既有规则与相关 skills 的替代、保留、配合关系已经解释；完整路径中的实际扩展与声明插件已经覆盖。用户点题或打断后的范围按用户要求处理。讲解结束直接说明后续适配或使用入口。

## 本机诊断、适配与安装

`check` 使用 `omp config path`、`omp config list --scope global --json`、`omp plugin list --json` 取得本机事实，再按 `.omp/commands/update-omp.md` 运行更新器的 `apply --source . --check` 和 `./plugin-audit.sh`。named profile 使用实际 agent 目录。报告已有能力、适配需求、更新影响和验证缺口，诊断保持只读。

用户要求适配时，以已有模型服务和需求形成方案，说明每项设置的用途、建议值与后续修改方式。推荐模型前用 `omp models <provider>` 核对推理强度与窗口；压缩规则按首个匹配检查实际覆盖模型，阈值小于各自窗口。提供商扩充可以是内置登录、提供商插件或自定义中转站，按宿主或插件资料处理。思考翻译等插件设置由插件来源指导。

已明确的选择直接执行；确实缺少个人选择时，用普通文字把决定及影响一次说明，收到回复后继续。这个方式同样用于冲突取舍与卸载候选，引用更新流程不会重新引入 `ask`。

写入前读 `agent/extensions/omp-config-autoupdate/omp-config-update.ts` 文件头和归属清单，确定本机项、首次播种项、可合并受管项和仓库代码如何处理。本机定制写在本机副本，保留其他已有内容；凭据由既有登录或 secret-store 注入路径处理，只读必要的非敏感设置，不回显凭据、不解密 SOPS、不访问 macOS Keychain。

安装复用 `.omp/commands/update-omp.md` 的完整流程，包括错误、冲突、插件审计和验证。当前更新器是全量安装，完整或轻量是使用入口的选择，差异从当前模式配置调查。用户要求写入前不创建 Todo；进入工作阶段后使用当前可用的工作记录工具，冷启动时将依赖原生 Todo 的工作在关闭它的更新步骤前收束。

交付时说明实际写入的定制、安装结果、待处理事项和生效时机。配置落盘、当前会话生效、重启加载分别核对；安装错误按更新流程解决后再重启。仓库工作树与操作前基线比较，保持用户原有改动不变。
