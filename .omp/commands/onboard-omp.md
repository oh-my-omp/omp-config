你是这次引导的调查者和讲解者。请亲自调查当前的 OMP 与 omp-config，理解这套组合为什么这样定制，再把你的理解讲给用户。范围包括基础配置、提示词、子代理定义、全部本地扩展和安装脚本声明的全部插件，含可选项。

读者是初次接触这套组合、想弄懂它为什么这样安排以及自己能怎样使用和定制的人。交付是一场使用与设计动机的介绍，不是开发者实现评审。

现有文档、仓库自带配置和下文线索都是调查参考，不是现成讲稿。解释来自你这次读到的资料和形成的认识。由主会话直接完成，不派 subagent。

本命令全程不用 `ask`。查清一组内容就直接讲，接着调查和讲下一组，连续完成；不逐步确认、不询问是否继续。用户可以随时用普通对话打断、点题或提出自己的配置需求。

当前参数：`$ARGUMENTS`。

- 参数为空：完整调查并讲解整套 omomp，保持只读。
- 参数是主题、扩展或插件名：直接调查并解释该项及理解它所需的关联。
- 参数为 `check`：执行本机只读诊断，见后文。
- 用户明确要求适配、安装或接入服务：进入本机操作流程，无需先听完整讲解。

兼容原有主题编号：1 文件修改，2 提示词与规则，3 长任务记忆，4 协作，5 执行监督，6 命令与安全，7 日常使用，8 模型与更新。编号只作入口，实际讲解顺序由你调查后的理解组织。

## 先建立本次调查的范围

先按参数确定本次范围。以下调查、理解和完整性核对都围绕这个范围展开。

完整讲解时，阅读 `README.md` 或中文版本了解设计出发点，再读 `agent/config.yml`、`agent/config-light.yml`、`agent/omomp.yml` 和 `install-plugins.sh`，看清当前组合。用 `glob` 发现 `agent/extensions/*/index.ts`、`agent/extensions-last/*/index.ts` 和 `agent/agents/*.md`，将提示词模板、主会话追加规则、`omp-light` 启动器也纳入理解。插件范围取安装脚本的实际声明，包括注释的可选插件。`_shared` 是实现辅助，不是另外一组需要用户学习的扩展。

用户点名主题或组件时，从该项自己的入口、配置和说明开始，沿理解它所必需的关联调查，再直接讲解该项。完整组合的发现清单用于完整讲解，不是单项介绍的前置作业。

用 `docs/` 中的相关页面帮助定位用途和关系，形成这次范围内的脉络，再按实际问题展开。本机安装状态和账号盘点留到 `check` 或本机适配时进行。

## 每一项都要自己读懂

对每个扩展，阅读入口的文件头、配置读取和主要行为；有具体疑问时沿相关调用读必要实现。对插件，阅读插件自己的 README；可以使用本地检出、已安装包或安装来源，行为和配置有疑问时再查它自己的实现。源码用于解答问题，不需要逐文件讲述。

对 OMP 原生能力及被替换的能力，查阅 `omp://settings.md`、`omp://tools/`、`omp://compaction.md` 等对应内置文档，弄清原生行为与当前 omomp 的差别。涉及模型接入时查 `omp://providers.md` 和 `omp://models.md`。冷启动使用当时已有的工具和文档入口。

调查要使你能回答：

- 用户在什么工作中会遇到这个问题？原生 OMP 或没有该插件时会怎样？
- 这一项增加、替换或调整了什么？为什么本仓库要把它放进这套组合？
- 哪些行为由实现提供，哪些由用户配置决定？仓库当前文件选用了什么示例策略？
- 它和其他项怎样配合，用户会看到什么变化，哪些运行条件和代价会影响使用选择？
- 用户要换成自己的偏好时可以改什么，配置在哪个范围生效，修改何时加载，更新如何处理？

用途由当前实现和拥有方资料核实，采用理由从仓库设计说明、接入关系及相关记录理解。把资料明说的原因与你根据行为得到的推断区分开。预备参考与当前实际情况不同时，继续查清差异，并按核实后的认识讲解。

## 把配置当作用户定制入口

omomp 通常把某种行为做成配置文件，就是为了让用户按自己的需要配置。仓库随附的内容是一组可运行的示例，不是要求所有用户遵循的唯一方案。

调查时把机制、配置接口和示例内容分开。先读配置 schema 和加载逻辑，理解扩展接受哪些用户策略、怎样决定有效配置，再看仓库如何使用它，最后解释用户怎样换成自己的策略。配置既可能是 `omomp.*` 的段，也可能是提示词片段、替换规则、回合判定、周期审阅或子代理定义；逐项核对作用域、覆盖或组合方式与生效时机。仓库示例在被加载时会实际运行，示例中的一个取值也不代表全部合法选择。

因此，讲解不止于“作者设了什么”。还要说明这个例子为什么这样写、哪些地方体现作者自己的模型和工作习惯、用户可以怎样重新组织。模型绑定、阈值、监督问题、提醒措辞、适用对象和模式等，都应沿着实际配置能力解释。个人化不是安装之后才允许考虑的例外，而是这次引导要帮助用户掌握的用法。

配置归属与合并规则决定更新时如何处理本机修改，不限制用户定制配置的权利。插件自己的配置方式到插件来源调查；本仓库的示例与插件自身的默认设置也分别说明。

## 查清一组，讲清一组，再继续

先用你调查出的整体认识解释为什么需要这套组合，再把相关项放进具体使用场景中展开。每个扩展和插件都要能被读者辨认，分别理解用途和采用原因；相互配合的项可以在同一段故事里讲出各自分工。

把调查结果先在自己的推理中整理成因果关系，再沿用户的实际工作讲述：一个任务怎样开始、哪里容易出问题、这些定制为什么在那个时刻出现、用户会感受到什么、又能按自己的需要改变什么。正文用连贯自然段讲清这些经历，组件名帮助辨认各自分工。读者要听的是你已经想明白的解释，不是你的技术调查记录；单独点名组件也沿用这一讲解层次。

可配置性讲到用户策略：能改变什么工作方式、仓库示例选了什么、换一种需求可以怎样组织、在哪个范围何时生效。完整性通过内部范围核对来保证，正文不铺配置值对照表、schema 字段列表或内部事件流程。具体语法留到用户实际要配置时说明，调用细节留到用户追问实现时展开。篇幅用在场景和理由上，影响使用选择的条件和代价随相应内容自然交代。

下列问题仅供寻找调查方向，具体答案和讲解顺序由你现场形成：

- 系统、工具、项目和模型各自带来的要求怎样共同作用？哪些定制是在整理冲突，哪些是在按场景补充？
- 文件读取、搜索和修改为什么选择现在的路径？原生工具的配置与本地扩展各自改变了什么？
- 任务记录、历史读取、背景继承和压缩分别保存什么？它们怎样支持同一个长任务？
- 执行者和顾问为什么分开？派发、并发、交付以及额度安排分别解决什么问题？
- 执行中、回合结束后和周期性的监督有什么不同？仓库示例选择了哪些问题、对象和提醒方式，用户还能怎样配置？
- 命令、终端、删除、工作区切换和重启怎样配合？完整和轻量入口分别保留了什么？
- 交互、语言、翻译、润色、展示、图片、工作文档和会话联络，各自在什么场景下有用？哪些属于日常工作流偏好？
- 提供商适配、远端构建和配置更新各自依赖什么环境？为什么有些随组合提供，有些只作可选声明？

这些不是固定章节或答案。读到新的关系，可以按更能解释因果的方式组织。每组讲完直接继续，不把调查进度或下一步变成用户选择题。

结束前对照实际扩展入口和插件安装声明，补齐尚未调查或解释的项。完整路径逐项覆盖；用户点题或打断后的范围按用户要求处理。讲解结束直接说明后续可做的本机适配或使用入口。

## 本机诊断、适配与安装

`check` 使用 `omp config path`、`omp config list --scope global --json`、`omp plugin list --json` 取得本机事实，再按 `.omp/commands/update-omp.md` 运行更新器的 `apply --source . --check` 和 `./plugin-audit.sh`。named profile 使用实际 agent 目录。报告本机已有能力、适配需求、更新影响和验证缺口，整个诊断保持只读。

用户要求适配时，以已有模型服务和用户需求形成方案，说明每项设置的用途、实际建议值和后续修改方式。推荐模型前用 `omp models <provider>` 核对推理强度与窗口；压缩规则按首个匹配检查实际覆盖的模型，阈值小于各自窗口。提供商扩充可以是内置登录、补充提供商插件或自定义中转站，按对应宿主或插件资料处理。思考翻译等插件设置由插件来源指导。

用户已经明确的选择直接执行；确实缺少个人选择时，用普通文字把需要决定的内容和影响一次说明，收到回复后继续。这个沟通方式同样用于安装中的冲突取舍和卸载候选，引用更新流程不会重新引入 `ask`。

实际写入前，读更新器 `agent/extensions/omp-config-autoupdate/omp-config-update.ts` 文件头和当前归属清单，确定本机项、首次播种项、可合并受管项和仓库代码各自如何处理。本机定制写在本机副本，保留其他已有内容；凭据通过既有登录或 secret-store 注入路径处理，只读取必要的非敏感设置，不回显凭据，也不解密 SOPS 或访问 macOS Keychain。

安装复用 `.omp/commands/update-omp.md` 的完整流程，按其错误、冲突、插件审计和验证步骤执行。当前更新器是全量安装，完整或轻量是使用入口的选择，具体差异从当前模式配置调查。用户要求写入前，调查和讲解不创建 Todo；进入工作阶段后使用当前可用的工作记录工具，冷启动时将依赖原生 Todo 的工作在关闭它的更新步骤前收束。

交付时说明实际写入的定制、安装结果、仍需处理的事项及生效时机。配置落盘、当前会话生效和重启后加载分别按当前实现核对，安装错误先按更新流程解决再重启。仓库工作树与操作前基线比较，保持用户原有改动不变。
